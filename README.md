# 台灣政府資訊系統委外文件 AI Skills

三個 skill，協助處理台灣政府機關資訊系統委外案的**工作說明書**、**服務建議書**與**履約交付文件**：

| Skill | 做什麼 |
| --- | --- |
| **tw-gov-it-docs** | **寫**。從 RFP 展開需求編號，搭章節骨架，逐章產出初稿，產生 Word 空白範本 |
| **tw-gov-it-review** | **審**。文件寫好之後，在送件前挑出會被機關退件的問題 |
| **tw-gov-ta-docs** | **顧問協辦寫工作說明書**。機關不熟悉技術、委由顧問代擬草稿時的獨立情境，自成一套骨架與判準，不依賴前兩個 skill |

**廠商端與機關端都能用。** 廠商端用撰寫端搭骨架與產 Word 範本、用審核端自檢；機關端用撰寫端寫工作說明書、用審核端在公告前自審；機關委由顧問代擬草稿時改用 `tw-gov-ta-docs`。省下來的是每份文件都要重做一次的大標小標、字體級數、表格欄位那一段工。

`tw-gov-it-docs` 與 `tw-gov-it-review` 是成對使用的一組：寫和審是兩件不同的事，寫的時候在意的是「該有的都有了嗎」，審的時候在意的是「這樣送出去會不會被退回來」，同一組規則從兩個方向用，混在一起會互相稀釋。`tw-gov-ta-docs` 立場與適用情境都不同，獨立成一個 skill，單獨安裝即可使用，見該 skill 的 `SKILL.md`。

## 為什麼需要這個

政府標案的文件不是寫給工程師看的，是寫給評選委員和驗收小組看的。他們檢查的是：

- 建議書有沒有對應到 RFP 的每一條需求與每一個評分項目
- 交付文件的章節有沒有齊全（缺章節在驗收時是硬傷）
- 需求 → 設計 → 測試 的追溯關係能不能對得起來
- 資安分級、無障礙、個資、原始碼歸屬有沒有交代

這些規則散落在各機關的需求說明書附件裡，新進的專案經理往往是被退件幾次才學會。這兩個 skill 把它們整理成 AI 可以依循的規範。

## 涵蓋範圍

**tw-gov-it-docs（撰寫）**

| 階段 | 文件 |
| --- | --- |
| 發包（機關端） | 工作說明書／需求說明書（RFP）、需求編號表、交付項目與驗收標準表、評選項目與配分表 |
| 投標 | 服務建議書、需求回應對照表、規格符合對照表、評選簡報大綱 |
| 履約 | 專案執行計畫書、需求規格書（SRS）、設計規格書（SDD）、測試計畫書與測試報告、使用手冊、系統管理手冊、教育訓練教材、需求變更與履約管理文件 |
| 上線 | 資料移轉計畫與報告、系統上線切換計畫（含冒煙測試與回復程序） |
| 結案 | 期中／期末報告、結案報告、交付項目對照表 |
| 維運 | 營運交接文件、維護月報、服務水準（SLA）報表 |
| 橫向 | 採購型態差異（最有利標／最低標、共同供應契約、雲端服務採購、**AI 專案**）、**填寫範例集** |

**tw-gov-it-review（審核）**

| 面向 | 審什麼 |
| --- | --- |
| 結構與格式 | 章節缺漏、封面與版本紀錄表、目錄與頁碼、階層編號、圖表編號與引用、追溯鏈斷點、跨文件一致性、敏感欄位有沒有被寫進去 |
| 機關端工作說明書 | 需求判不判得出合格、綁標之虞、需求編號與驗收標準對不對得上、與投標須知及契約條款的六項匹配 |
| 用詞用語與表達 | 簡體字、中國大陸用語、法律統一用字、無法驗收的模糊字眼、行銷形容詞、標點與全半形、序數的數字用法、句型問題 |
| 法規名稱 | 現行法規速查表、已停止適用不得再引用的舊名稱、資安兩套分級的觀念錯誤 |

**tw-gov-ta-docs（顧問協辦寫工作說明書）**

機關委由顧問（或系統整合商）代擬工作說明書草稿時的獨立情境：顧問手上沒有機關內部事實（預算、既有系統、
內部簽核期程），卻要交出精確到能送審的文件。骨架章節與措辭取自實際結案案例，機關專屬事實與每案不同的
數字（金額、期限、比例、規格）一律留白為 `○○○`，交機關確認，不代為編造。與前兩個 skill 各自獨立，
不共用骨架或判準。

產出的 Word 直接套同一份結案案例的版面範本：字體、字級、縮排、行距、頁面邊界、頁首頁尾都來自範本，
壹／一／（一）／1./(1) 五層標號是 Word 的自動編號而非打上去的字，機關收到後在 Word 裡插入或搬動章節
會自動重編。
| 法規名稱 | 現行法規速查表、已停止適用不得再引用的舊名稱、資安兩套分級的觀念錯誤 |

## 與公文 skill 的分工

這兩個 skill 只處理**技術文件**。**公文書**（函、令、公告、開會通知單）與存證信函、陳情書、合約屬另一套體例，請搭配公文 skill，例如 [tw-formal-writing](https://github.com/Imbad0202/tw-formal-writing)。

判斷準則：**這份文件會不會用機關發文字號發出去？** 會，就是公文書。

履約期間要行文給機關（展延申請、需求變更陳報、履約爭議、驗收申請）時，公文本體交給公文 skill，這兩個 skill 負責附件的技術內容。

## 匯入方式

**Claude Code**（推薦，可用到 assets 與腳本）
```bash
cp -r skills/tw-gov-it-docs skills/tw-gov-it-review ~/.claude/skills/
# 機關委由顧問協辦撰寫工作說明書時，另外裝這個（獨立，可單獨使用）：
cp -r skills/tw-gov-ta-docs ~/.claude/skills/
```

**Claude（claude.ai）**
1. 建立一個 Project
2. 在 Project Knowledge 上傳 `STANDALONE.md`——`tw-gov-it-docs` 與 `tw-gov-it-review` 兩份成對上傳；`tw-gov-ta-docs` 是獨立情境，只在需要時單獨上傳
3. 在該 Project 中開始對話

**ChatGPT Projects / GPTs**
上傳對應的 `STANDALONE.md` 作為 Knowledge，Instructions 填：
> 你是台灣政府資訊系統委外文件撰寫與審查專家。撰寫依撰寫版 STANDALONE.md，審查依審查版 STANDALONE.md。動筆前先確認文件類型與來源 RFP，產出後跑一遍審查版的三道檢查。機關委由顧問協辦撰寫工作說明書時，改依 tw-gov-ta-docs 版 STANDALONE.md。

**Gemini Gems**
將對應的 `STANDALONE.md` 內容貼入指示欄位。

## 使用範例

**要寫東西的時候**

- 「這是機關的需求說明書，幫我列出建議書應該有哪些章節，並做一張需求回應對照表」
- 「幫我寫這個案子的專案執行計畫書初稿」
- 「我們要交系統管理手冊，該寫哪些東西？」  <!-- 檢查略過 -->
- 「這案要做舊系統資料移轉，幫我列資料移轉計畫的章節和欄位對應表」
- 「這是共同供應契約的案子，交付文件要準備哪些？」
- 「幫我把這條 RFP 需求展開成 SRS 的功能需求條目和測試案例」
- 「幫我產生需求規格書的 Word 空白範本，機關是○○部」

**機關端要發包的時候**

- 「我是機關承辦人，要寫這案的工作說明書，先給我章節大綱」
- 「幫我把這幾條需求改寫成驗收時判得出合格的寫法」
- 「這份需求說明書公告前幫我自審一遍，有沒有綁標之虞或判不出合格的條文」
- 「幫我從工作說明書的需求編號，反推交付項目與驗收標準表」
- 「這案是最有利標，幫我擬評選項目與配分表，並對到建議書章節」

**東西寫完之後**

- 「這份設計規格書送出去會不會被退件？」
- 「幫我檢查這份文件有沒有缺章節」
- 「這份建議書幫我檢查用語，有沒有簡體字、大陸用語或不能驗收的字眼」
- 「這份 SRS 的需求追溯表對得起來嗎？」
- 「交件前幫我跑一遍檢核」

> 用語檢查、Word 範本產生都由 skill 代勞，直接用上面的句子交代即可，不需要自己記指令。

## 送件前的例行查證

文件裡只要寫了範本或指引的**版本號**，送件前跑一次（約 30 秒）：

```bash
python skills/tw-gov-it-review/scripts/check_sources.py --只看異動 --嚴格
```

沒有輸出就是沒有異動。跳出 `[異動]` 表示官方已改版，**該版本號在送出的文件中不可再引用**，處理步驟見 `skills/tw-gov-it-review/references/04-來源與查證.md`。

`--嚴格` 是給送件前用的：有來源連不上時回離開碼 2 而非 0。**連不上不等於沒異動**，那幾項這次沒查證到，該重跑或人工開頁面看。

這不是形式主義：投標須知範本近一年改版四次（1140328、1140703、1141231、1150727），本專案就曾讓過時三年的版本號留在文件裡。

倉庫另有 `.github/workflows/check-sources.yml`，每月 1 日自動查證一次，發現異動會開 issue（標籤 `source-check`）。手動觸發走 GitHub 的 Actions 頁面。

## 注意事項

**依《行政院及所屬機關（構）使用生成式 AI 參考指引》，機密文書應由承辦人親自撰寫。** 請勿輸入機關未同意公開的網路架構、實際 IP、帳號密碼原則、資安設定值，或與案件無關的個資。

本工具產出初稿與審查意見，不取代廠商內部覆核與機關承辦人確認，也不取代正式的投標與履約程序。各機關的交付項目要求略有差異，**若機關已提供「交付項目文件說明」附件，一律以機關版本為準。**

## 目前的限制

- **已對照官方規範校準，但未對照實際標案文件校準。** 章節規格、SLA 項目、採購與資安要求已逐條對照上列官方指引與範本；但**單一機關實際發出的需求說明書與驗收通過的交付文件仍未取得**——這類文件通常只隨招標文件發給投標廠商，網路上幾乎不公開。若你手上有，請據以校對章節名稱與用語，機關的實際寫法一律優先。
- 範例集中的機關、案名、人物、數值**全部虛構**，僅示範格式與顆粒度，不得直接沿用。
- 各機關差異大，這兩個 skill 提供的是通用底稿，**機關版本一律優先**。
