# 機關端工作說明書撰寫

本檔是機關承辦人撰寫工作說明書（或稱需求說明書、建議書徵求文件）時的撰寫要點；章節骨架見 `assets/13-工作說明書骨架.md`。

其餘各檔的立場都是廠商端。**進入本檔就換立場**：使用者是機關承辦人，寫出來的文件會被廠商拿去投標，而不是被機關審查。

> **本檔不引用《政府採購法》條號。** 招標程序、決標方式、爭議處理的法律要件依機關的採購或總務單位辦理；本檔只談「需求怎麼寫」。
>
> **各節的判斷方法、好壞寫法對照與範例句為依通用實務自行撰寫**，非官方規範文字，撰寫時不得宣稱為官方規範。
>
> **「工作說明書」不是官方用語。** 工程會 59 份招標文件範本中沒有任何一份名為工作說明書、需求說明書或建議書徵求文件，
> 官方一律以上位詞「**招標文件**」稱之。本檔與骨架沿用業界慣稱，實際撰寫時**以機關慣用名稱為準**。

## 一、成敗判準不一樣

| | 廠商端交付文件 | 機關端工作說明書 |
| --- | --- | --- |
| 寫壞的代價 | 被退件、扣分、驗收不過 | 廠商投標前提一堆疑義、決標後認定不一、驗收時無從判定合格 |
| 寫作重心 | 證明「每條需求都回應了」 | 讓「每條需求日後都判得出合格與否」 |
| 最怕的事 | 章節缺漏 | 需求寫得含糊，或需求規模超出預算 |

廠商端可以用篇幅補救寫得普通的段落；機關端不行——**含糊的一句話會在履約期間被雙方各自解讀**，而那時候文件已經不能改了。

## 二、需求編號是機關的事

追溯鏈的起點在工作說明書，不在建議書：

```
工作說明書需求編號 → 建議書回應對照 → 軟體需求 → 設計元件 → 驗證方式 → 測試案例
```

機關不編號，廠商就會各編各的：A 廠商的 R-013 與 B 廠商的 R-013 不是同一條，決標後還要重新對一次；驗收時委員拿工作說明書逐條核對，也找不到對應的測試案例。

**機關在公告階段就把需求編號寫進文件**，後面所有文件都用同一組編號，這是整組 skill 裡投資報酬率最高的一個動作。編號前綴沿用 `assets/00-共通元件.md` 的代號編定規則。

編好之後做一件事：把每個編號填進骨架第陸章的驗收標準表。**填不出合格判準的需求，就是還沒寫清楚的需求**——這個檢查比讀三遍還有效。

顆粒度參考 `references/03-範例集.md` 第一節（一）（二），該處示範同一條需求從說明書條文到編號表的樣子。

## 三、需求怎麼寫才判得出合格

需求規格不明確是機關端最常見的問題。判斷方法：**把這句話交給兩個不認識的人，他們會不會做出不同的東西？**

| ✗ 判不出合格 | ✓ 判得出合格 |
| --- | --- |
| 系統應具備良好的效能 | 並行使用者 200 人時，查詢頁面回應時間 3 秒內（95 百分位），以壓力測試報告查驗 |
| 應提供完善的報表功能 | 應提供附錄三所列 12 種報表，均可匯出為 ODF 與 PDF 格式，並可依承辦人設定之條件篩選 |
| 系統應具備高度安全性 | 應通過弱點掃描與滲透測試，中度以上風險項目均已修復並提出複測報告 |
| 廠商應配合機關需求辦理教育訓練 | 應辦理 3 場次、每場 3 小時之教育訓練，對象為承辦人 60 人，並提供教材與全程錄影 |
| 應與既有系統介接 | 應與人事差勤系統介接，每日 02:00 以 Web API 取得異動人員資料，格式見附錄三，失敗時重試 3 次並以電子郵件通知系統管理者 |

共通點：左欄是形容詞，右欄是**數量、時點、格式、對象、失敗時怎麼辦**。寫不出右欄的欄位，代表這件事機關自己還沒想清楚，先留 `【待填：○○】` 並在公告前補實，不要用形容詞蓋過去。

同一個道理反過來用：**別把「機關還沒決定的事」寫成廠商的義務**。「依機關屆時指定之格式辦理」這種寫法，廠商無法估價，投標時只能往高報或事後爭議。

## 四、避免綁標之虞

兩種常見寫法會被質疑：

- **規格只有單一廠商符合。** 逐條檢視硬性規格：這一條是本案真的需要，還是抄自某家產品的型錄？指定品牌或型號時載明「或同等品」，並寫出同等品的認定方式（由誰認定、要提出什麼證明、何時提出）。
- **就現有廠商所提建議直接改寫成需求。** 蒐集廠商資訊本身是正當的，但直接沿用其用語與規格組合，會讓其他廠商認為不公。改寫成功能性描述——寫「要達成什麼」，不寫「要用哪一套產品達成」。

檢查方式：把硬性規格單獨拉一張表，每一條問一句「不符合這條的廠商，是真的做不到本案的事嗎」。答不出來就放寬。

## 五、交付項目怎麼訂

**先對齊契約範本的用語。** 契約範本第二條（二）「應用軟體系統開發服務」項下明列廠商應提供履約標的所依據的文件：**工作計畫書、需求規格書、系統分析書、程式設計書、測試計畫書、執行報告書、教育訓練計畫書、軟硬體清冊及系統架構圖**。這是目前唯一有契約效力的文件清單，與業界慣稱的 SRS／SDD 對應如下：

| 契約範本第二條（二）用語 | 業界慣稱 | 對應骨架 |
| --- | --- | --- |
| 工作計畫書 | 專案執行計畫書 | `assets/02` |
| 需求規格書 | SRS | `assets/03` |
| 系統分析書、程式設計書 | 設計規格書（SDD） | `assets/04` |
| 測試計畫書 | 測試計畫書與報告 | `assets/05` |
| 教育訓練計畫書 | 教育訓練教材 | `references/02` 第七節 |
| 執行報告書 | 期中／期末／結案報告 | `assets/08` |
| 軟硬體清冊、系統架構圖 | 營運交接文件的一部分 | `assets/11` |

**工作說明書用哪一組名稱都可以，但要與契約一致。** 用業界慣稱時，在交付文件表加一欄註明對應契約第二條（二）的哪一項；不然驗收時會出現「契約要系統分析書，廠商交 SDD」的爭執。

契約範本另定的兩項，工作說明書漏了廠商就不會做：

- **介接**：第二條（四）——履約標的涉及共通性應用程式介面開發或整合者，應依國家發展委員會訂定之「共通性應用程式介面規範」辦理。
- **開放格式資料**：第二條（二）——可勾選 XML、CSV、JSON、KML、SHP，並應每○月定期產製並銜接政府資料開放平臺更新。頻率由機關於招標時載明。

骨架第參章之十一的交付文件表，就是廠商端「交付項目文件說明」附件的來源。訂的時候三件事：

1. **只列真的會查的文件。** 列進去就要在驗收時逐份查對；列了不查，下一案的廠商會知道這張表是形式。
2. **附上章節要求。** 只寫文件名稱，各廠商交來的內容深淺差很多。直接引用 `assets/` 對應骨架的章節名稱（SRS 用 `assets/03-需求規格書骨架.md`，SDD 用 `assets/04-設計規格書骨架.md`，依此類推），各文件應涵蓋的內容見 `references/02-交付文件規格.md`。
3. **綁交付時點與查核點。** 每份文件掛在哪一個查核點交、審查通過才付款，寫在骨架第伍章。

**不要把交付文件表照抄。** 維護服務案不需要 SDD，共同供應契約案不需要 SRS——採購型態對應的文件差異見 `references/05-採購型態.md`。

## 六、服務水準訂太嚴或太寬都是問題

過嚴會讓廠商必然違約（訂不到的承諾等於沒有承諾，且會反映在投標價格上）；過寬則上線後效能不彰卻無從追究。

訂之前先確認三件事：**機關自己的維運時段是幾點到幾點**、**故障通報的窗口與方式**、**機關端配合的時限**（例如廠商需機關開通權限才能修復時，機關要多久給）。第三項沒寫，SLA 的修復時間就無法歸責。

項目選用見 `references/04-履約與維運文件.md` 第五節，該節的欄位機關端與廠商端共用。

## 七、需求規模要與預算相稱

需求明顯超出預算，優良廠商不投標，剩下的是低報後在履約階段要求變更的廠商。

定稿前做一次對稱檢查：把功能需求依規模分級，對照預算與履約期限，看得出來做不完的部分，改列為「選擇性需求」或移到後續年度。**選擇性需求要標示清楚**，並說明是否納入評選與計價。

經費估算依「政府資訊服務採購經費估算編列手冊」辦理，並依「政府資訊服務採購作業指引」**按比例編列資安預算且單獨列項**。實際級距與比例依現行版本，本檔不提供數值。

**估算結果要成為招標文件的一部分。** 投標須知範本（115.7.27 版）第七十九點「全份招標文件包括」第 (8) 項為「**資訊服務採購案，資訊服務費用估算表**」——這張表與工作說明書一起發給領標廠商。因此需求規模與估算表要對得起來：估算表列了教育訓練 3 場，工作說明書寫 10 場，廠商投標前就會提疑義。

同點另可看出**工作說明書在招標文件裡的位置**：第七十九點列的九項中沒有「工作說明書」「需求說明書」，它歸在第 (6) 項「**招標規範**」之下（第 (1)～(5) 項與 (7) 項為投標須知、契約條款、標價清單、聲明書、切結書等制式文件）。這也是第九節「工作說明書屬招標文件內之其他文件」的由來。

## 八、評選項目與配分表

**先確認它該放哪裡。** 投標須知範本（115.7.27 版）第五十八點決標原則：「(2)最有利標（**評選項目、標準及評定方式如附件**）」——官方定位是**投標須知的附件**，不是工作說明書的一章。機關實務上常與需求說明書一併發布，兩種做法都行得通，但定稿時要確認「評選項目表只有一份、且投標須知指得到它」。骨架把它放在第玖章是為了讓承辦人一次寫完，不是主張它屬於工作說明書。

**建議書的頁數與份數規定，投標須知範本裡沒有。** 該範本全文未出現「建議書」「頁數」，份數僅一處。這些屬機關自訂，可寫在投標須知第八十三點「其他須知」或工作說明書，擇一即可，不要兩邊都寫。

僅最有利標適用。三個原則：

- **每個評選項目都要在本文件找得到對應需求。** 評「系統開發能力」卻沒有對應的功能需求章節，委員只能憑印象給分。
- **配分反映重要性。** 配分決定廠商的篇幅配置——「公司實績」給 30 分，收到的建議書就會有一半在講公司。
- **建議書章節順序與配分表一致。** 寫進骨架第玖章之一，委員評分時逐章對逐項，不必翻找。

配分表本身的法定要件（委員組成、評分方式、加權計算）依機關採購單位辦理，本檔不涉及。

## 九、與投標須知、契約條款的匹配

投標須知與契約條款多由採購或總務單位以範本產生，工作說明書由資訊承辦人研擬，兩者容易矛盾。

**矛盾時誰優先，契約範本自己寫了。** 資訊服務採購契約範本第一條（三）1：「招標文件內之投標須知及契約條款優於招標文件內之其他文件所附記之條款。但附記之條款有特別聲明者，不在此限。」工作說明書屬「招標文件內之其他文件」，因此**矛盾處以投標須知與契約條款為準，改工作說明書**；確有必要以工作說明書為準時，須在該條款特別聲明。

### 契約範本的預設值——寫之前先知道你在改什麼

| 事項 | 契約範本條號 | 預設值／未載明時適用 |
| --- | --- | --- |
| 履約期限起算 | 第七條（一） | 由機關勾選：決標日／機關簽約日／機關通知日／收到信用狀日 |
| 日曆天或工作天 | 第七條（二） | **未勾選者為日曆天** |
| 廠商提出工作計畫（或建議書）期限 | 第八條（二）1 | 得標後○日；**未載明者 20 日** |
| 機關核定廠商建議書期限 | 第二條（三） | ○日；**未載明者 10 日** |
| 分期付款 | 第五條（一） | 機關 15 工作天內完成審核，接到請款單據後 15 工作天內付款；**涉及補助款者 30 工作天** |

| 無初驗程序 | 第十二條（二） | 機關於接獲備驗通知後 **30 日**內驗收 |
| 部分先行使用 | 第十二條（四） | 應先就該部分辦理驗收或分段查驗 |
| 保固期起算 | 第十三條（一） | **自全部完成履約經驗收合格日起**算 |

| 逾期違約金上限 | 第十四條（五） | 契約價金總額之 __%，**不高於 20%；未載明者為 20%** |

### 智慧財產權不是二選一

契約範本第十六條（三）5 列 **A 至 L 共 12 種約定方式**供機關勾選，從「廠商為著作人、機關取得指定的著作財產權授權」（A，另勾選重製權、編輯權等 10 項）到「以機關為著作人並取得著作財產權全部」（H）都有。範本註釋明白寫著「**機關亦宜考量避免因取得不必要之權利而增加採購成本**」，並建議非完全客製化的著作（如共同模組）約定由廠商享有著作財產權、機關取得非專屬永久無償利用權。

**所以工作說明書不要只寫「著作財產權歸屬機關」**，要寫出對應契約第十六條（三）5 的哪一個選項與哪幾項權利。

另兩項常被漏掉：

- **機關資料的所有權**：第十六條（三）4 已明定廠商所取得或持有機關之資料皆屬機關所有，工作說明書重複寫無妨，但不要寫出比契約更弱的版本。
- **開源軟體**：第十六條（三）6 要求以執行檔及原始碼共同提供，並交付開源軟體清單。

### 逐項比對清單

履約期限、付款期別與比例、保固起算時點、逾期違約金比率與上限、智慧財產權選項、驗收天數與有無初驗——六項逐一比對，數字要能對到上表的條號。

## 十、這些不要寫進去

工作說明書會隨招標公告發給所有領標廠商，**等同對外公開**。

- 機關實際 IP、內部網路架構圖、防火牆規則、資安設定值、系統帳號與密碼原則細節——一律留 `【待填：○○】`，於決標後以安全方式提供得標廠商。
- 承辦人以外的個人資料、機關內部簽核意見、預算編列的內部討論過程。

依《行政院及所屬機關（構）使用生成式 AI 參考指引》，機密文書應由承辦人親自撰寫，且不得向生成式 AI 提供涉及機密業務或個人資料之訊息。
