# 交付文件規格

本檔依台灣機關委外案常見的「交付項目文件說明」附件整理。各機關細節略有差異，但骨架高度一致。若使用者手上有機關版本的交付項目說明，**以機關版本為準**，本檔僅補其未列的部分。

## 文件名稱先對上契約

本檔各節使用業界慣稱（SRS、SDD）。**有契約效力的名稱是另一組**：資訊服務採購契約範本（113 年 12 月 26 日修正）第二條（二）「應用軟體系統開發服務」項下明列廠商應據以提供履約標的之文件為「工作計畫書、需求規格書、系統分析書、程式設計書、測試計畫書、執行報告書、教育訓練計畫書、軟硬體清冊及系統架構圖」。

| 契約範本第二條（二） | 本檔章節 |
| --- | --- |
| 工作計畫書 | 一、專案執行計畫書 |
| 需求規格書 | 二、需求規格書（SRS） |
| 系統分析書、程式設計書 | 三、設計規格書（SDD） |
| 測試計畫書 | 四、測試計畫書與測試報告 |
| 教育訓練計畫書 | 七、教育訓練教材 |
| 執行報告書 | 八、期中／期末報告與結案報告 |
| 軟硬體清冊、系統架構圖 | 見 `04-履約與維運文件.md` 第四節營運交接文件 |

使用手冊、系統管理手冊、資料移轉與上線切換計畫為契約範本未列、由機關自行加訂者。**交付文件清單用哪一組名稱都可以，但要標出對應項**，否則驗收時會出現「契約要系統分析書，廠商交 SDD」的爭執。

## 一、專案執行計畫書

通常是決標後第一份交付物。**期限先看契約**：資訊服務採購契約範本（113 年 12 月 26 日修正）第八條（二）1 規定廠商應於得標後 ○○ 日提出工作計畫（或建議書），**未載明者為 20 日**；機關核定的期限依第二條（三），未載明者為 10 日。各機關另訂 14 或 30 日者不少，以該案契約與招標文件所載為準。

| 章節 | 應涵蓋內容 |
| --- | --- |
| 計畫概述 | 計畫名稱、計畫目標、專案範圍及時程 |
| 專案工作項目與進行方式 | 現行系統作業環境、專案工作項目、工作時程規劃、系統測試、教育訓練、系統介接、專案驗收 |
| 交付項目與時程 | 工作項目與重要查核點、交付文件與要求 |
| 專案組織與權責 | 專案權責、專案組織架構 |
| 專案管理 | 專案監控、建構管理、各階段細節（系統分析、系統設計及資料庫設計、單元測試、整合測試、系統建置及上線、系統保固維護）、問題追蹤與管制、風險管理、需求變更管理、品質保證管理、專案報告 |
| 系統管理與安全 | 系統備援、整體操作及回復措施、系統安全、程式建構 |

撰寫要點：這份文件會被拿來當履約管理的依據，寫下的查核點與時程日後都要達成。時程要留緩衝，不要為了漂亮而壓縮。

## 二、需求規格書（SRS）

| 章節 | 應涵蓋內容 |
| --- | --- |
| 前言 | 1. 現行作業檢討：現行作業方式與待調整事項；相關業務規章細則、處理辦法與法律條文對系統開發的限制；就軟硬體資源、業務辦法、法律條文、系統轉換、人力支援等因素說明對新需求之限制；系統設計之對象、目的、範圍、系統環境、環境介面、處理需求、作業時機與週期；新系統功能需求、作業方式、電腦處理內容及作業程序<br>2. 標的軟體系統摘述<br>3. 定義與縮寫符號<br>4. 參考資料 |
| 文件目的與系統描述 | 系統功能目的；系統使用者種類特性——依實際操作特性區分（一般操作者、管理階層使用者、系統管理者等），以便功能測試時考量 |
| 系統功能需求 | 功能需求、非功能需求、介面需求、測試需求；功能需求另須描述本案可蒐集或產製之**開放資料類型、開放格式及更新機制** |
| 需求追溯表 | 以表列方式列出：徵求建議書需求、軟體需求簡述、設計元件、驗證方式、單元測試案例編號、整合測試案例編號 |
| 附錄 | 需求訪談紀錄、相關表單與事務流程圖 |

撰寫要點：
- 需求追溯表是驗收的主要查核工具，五個欄位缺一不可。設計元件與測試案例編號在 SRS 階段可先留編號規則，後續文件填實。
- 非功能需求要量化：效能（並行使用者數、回應時間）、可用度、備份頻率、保存年限、瀏覽器相容範圍。
- 使用者種類的區分直接決定權限矩陣，早點定清楚。
- 開放資料需求常被漏掉。機關的 RFP 若提到開放資料，SRS 要寫出資料集項目、開放格式、更新頻率與發布方式，並掛回需求編號。**契約範本第二條（二）已把它列為可勾選的履約標的**：開放格式為 XML、CSV、JSON、KML、SHP（另可由機關自訂），並應每 ○○ 月定期產製並銜接**政府資料開放平臺**更新，頻率由機關於招標時載明。SRS 的開放格式欄位照這組寫。
- **介接需求涉及共通性應用程式介面開發或整合者，應依國家發展委員會訂定之「共通性應用程式介面規範」辦理**（契約範本第二條（四））。SRS 的系統介接介面一節要寫明是否適用及依循方式。

**RFP 與交付文件的用詞不一樣，不要互相取代。** 機關寫 RFP 時的需求分類（依「政府資訊服務採購作業指引」的前身文件與各機關慣例）與 SRS 的章節用詞有固定對應：

| 機關 RFP 常用的詞 | SRS／交付文件對應的詞 |
| --- | --- |
| 功能需求 | 功能需求 |
| **品質屬性需求**（回應能力、資料處理量、可用性、可靠性、可維護性） | **非功能需求** |
| 技術需求（採用之技術方法與工具、應符合之國家標準與業界標準） | SRS 的限制條件、SDD 的技術架構 |
| 環境需求 | SRS 的系統環境、SDD 的部署架構 |
| 系統發展需求（生命週期各階段應遵循之標準、規範、方法與工具） | 專案執行計畫書的開發方法與標準 |
| 系統測試及上線需求（含平行測試、壓力測試、上線作業程序） | 測試計畫書＋系統上線切換計畫 |
| 技術移轉需求（技術移轉方式與項目、系統架構與配置、網路配置） | 教育訓練教材＋營運交接文件 |
| 資訊安全需求 | SRS 安全需求＋SDD 安全機制＋系統管理手冊 |

**做需求回應對照表時，左欄一律照抄機關 RFP 的原用詞**，右欄才寫本案文件的章節名稱。把機關的「品質屬性需求」改寫成「非功能需求」放進對照表左欄，委員會找不到對應。

## 三、設計規格書（SDD）

| 章節 | 應涵蓋內容 |
| --- | --- |
| 定義與縮寫符號 | 依使用者需求及系統功能定義縮寫符號 |
| 文件目的與系統描述 | 設計規格書之目的、系統範圍與目標 |
| 參考文獻 | 參考資料或資料索引 |
| 設計方法與工具 | 使用之程式語言；開發工具及其版本 |
| 組織架構 | 系統組織架構、系統軟硬體環境 |
| 系統流程 | 相關系統流程圖 |
| 模組關係規劃 | 各子系統功能以圖形表示，顯示輸入資料、檔案、輸出資訊間之關聯性 |
| 軟體元件規格 | 元件規格清單（元件代號、名稱），依代號排列；每一元件的功能描述、輸出入參數、邏輯流程、呼叫方法、相關元件、資料表及主要對應欄位 |
| 介面設計規格 | 介面清單（代號、名稱），依代號排列；逐一介面的功能描述、輸出入畫面、相關元件或輸出入資料表 |
| 報表格式設計 | 報表清單（代號、名稱、內容），依代號排列 |
| 程式功能說明 | 程式清單（程式代號、名稱、所屬功能/作業）；程式功能說明、處理邏輯（輸入、輸出、處理程序、存取資料、計算條件）、使用資料表及主要欄位、使用元件、使用介面；軟體整合說明（本系統與其他系統之整合機制與介面呼叫說明） |
| 程式目錄 | 程式存放位置（程式目錄、程式代號），依目錄排列 |
| 資料結構設計規格 | 系統所使用的特殊演算法、資料庫結構與資料庫關聯 |
| 檔案設計 | 檔案列表（代號、名稱）；系統相關檔案結構圖，說明檔案資料流向 |
| 資料庫設計規格 | 資料庫列表；資料表格列表；資料表格定義（表格代號、名稱、資料庫代號與名稱、欄位代碼、鍵值、型態及長度、欄位名稱、資料項目檢查方法）；資料儲存媒體；資料更新頻率；備份方法與頻率 |
| 例外處理 | 以文字、程式碼及流程圖說明軟體中所採用的例外處理設計 |
| 備份與回復機制說明 | 系統程式與資料庫的備份與回復機制規劃 |
| 安全機制說明 | 軟體安全機制設計，如防止資料隱碼（SQL Injection）攻擊之機制 |
| 需求追溯表 | 規格設計與需求對照，說明所有需求是否均已設計 |
| 附錄 | 相關單證或報表 |

撰寫要點：
- 代號體系要一次定好並全文一致（如 M-001 元件、UI-001 介面、RPT-001 報表、PRG-001 程式、DB-001、TB-001）。驗收時委員會抽查代號能否互相對得起來。
- 這份文件的份量最大，通常也是被退件最多次的一份，多半是因為「清單有但明細沒有」或「明細有但清單漏列」。清單與明細的筆數要對得上。

## 四、測試計畫書與測試報告

機關版交付清單有時把測試併入其他文件，但實務上分開較清楚。

**測試計畫書**：測試目的與範圍、測試環境（軟硬體、測試資料準備方式）、測試種類（單元、整合、系統、使用者驗收測試、效能測試、資安檢測）、測試案例設計（案例編號、對應需求編號、前置條件、測試步驟、預期結果）、測試進度與人力、缺失分級與處理流程、測試通過標準。

**測試報告**：測試執行摘要、各測試案例執行結果（含實際結果、通過與否、執行人、執行日期）、缺失清單與修正紀錄（缺失編號、分級、發現日期、修正日期、複測結果）、未結案缺失與風險說明、測試結論。

要點：測試案例編號必須回連 SRS 需求追溯表的欄位。缺失要留下「發現→修正→複測通過」的完整軌跡，只給一份「全部通過」的報告會被質疑。

## 五、使用手冊

| 章節 | 應涵蓋內容 |
| --- | --- |
| 文件目的與系統描述 | 文件目的、系統功能摘要、系統目標 |
| 功能／作業操作說明 | 功能與作業描述、頁面說明、操作步驟、欄位之限制條件與資料計算方法 |
| 疑難排除 | 線上錯誤訊息、線上協助操作系統、協助操作系統之書面說明、常見問題及問題處理程序 |
| 附錄 | 相關服務申請表單、代碼表 |

要點：讀者是不熟電腦的承辦人。每個操作步驟配一張截圖，步驟用編號，畫面元素用紅框標示。欄位限制條件（必填、格式、長度、可選值）要逐欄列表，這是使用者最常回頭查的內容。

## 六、系統管理手冊

| 章節 | 應涵蓋內容 |
| --- | --- |
| 軟、硬體環境需求 | 系統發展環境所需軟硬體及設備特性、處理速度、記憶體容量、系統軟體使用規則、備份與復原處理、系統安全管理及注意事項；應含硬體需求、作業系統及軟體需求、系統軟硬體架構圖、網路架構圖、使用者端所需環境說明 |
| 安裝指南 | 系統軟硬體建置之逐步程序，含安裝步驟與注意事項。安裝設定項目如：磁碟分割使用格式、資料庫安裝及設定、資料轉換服務安裝及設定、應用程式安裝及網頁伺服器設定、系統服務清單、設定檔參數設定、通訊埠設定及說明、稽核軌跡設定原則、系統事件日誌設定原則、系統修正更新設定、螢幕保護裝置設定 |
| 管理與操作機制 | 1. 使用者控管機制：內建帳戶與系統管理員帳戶之安全、通行碼控管原則、帳戶鎖定原則、使用者代碼規劃及管理（以表列說明權限分類、功能概述、目錄存取權限、群組、使用者），並說明匿名或訪客類帳戶是否必要及是否關閉、使用者帳戶設定步驟<br>2. 主機操作機制：主機代號、名稱、IP 位址、主機說明、開關機順序<br>3. 目錄檔案管理機制：以表列說明目錄檔案存取權限（目錄檔案、用途、R/W/X）、群組／使用者、擁有者帳號<br>4. 遠端遙控服務之控管方式<br>5. 對外提供網際網路服務時之安全規劃（如 FTP、Telnet、SMTP、POP3、NetBIOS 等服務埠） |
| 例行檢測方式 | 設備檢查機制、資料庫檢查機制、應用程式檢查機制、網路連線與防毒更新、檔案保留期限、限制容量及清理方法 |
| 備份還原設定及管理 | 系統之備份步驟與還原步驟 |
| 問題排除 | 常見問題及問題處理程序 |
| 附錄 | 相關管理資料表單 |

**這份文件敏感度最高。** 實際 IP、帳號、密碼原則、開放埠清單一律以 `【待填：由機關承辦人補實】` 標示，不要生成看似真實的數值。定稿版通常列為機密文件，不得對外流通。

## 七、教育訓練教材

包含：訓練計畫（對象分級、場次、時數、地點、講師）、簡報教材、學員手冊、上機演練腳本、測驗題與問卷、訓練成果報告（簽到表、照片、問卷統計、意見回饋與改善說明）。

要點：機關驗收看的是「有沒有辦、有沒有紀錄」，簽到表與問卷統計不能少。訓練對象至少分「一般使用者」與「系統管理者」兩級，教材要分開。

---

## 八、期中／期末報告與結案報告

**期中報告**：期程進度對照（計畫 vs 實際）、已完成工作、系統展示範圍、遭遇問題與因應、需求變更彙整、下階段工作計畫與風險。

**期末／結案報告**：全案工作成果總覽、交付項目清單與繳交狀況對照表、需求達成情形（回連需求追溯表逐條列出達成與否）、測試與資安檢測結果、教育訓練辦理情形、系統上線狀況、後續保固維護安排、經驗與建議事項。

要點：交付項目清單對照表是驗收會議上翻最多的一頁，把它放在最前面。進度落後的項目據實說明並附因應措施，隱瞞在驗收時被發現更難處理。

---

## 九、文件共通要求

每一份交付文件都應具備：

1. **封面**：機關全銜、案名、文件名稱、廠商名稱、版本、日期。
2. **文件版本紀錄表**：版本、日期、修訂內容摘要、修訂人、審核人。機關常要求保留完整修訂歷程。
3. **目錄**：含圖目錄與表目錄。
4. **章節編號一致**：全案所有文件採同一套編號規則。
5. **份數與媒體**：紙本份數依契約，電子檔通常要求可編輯格式與 PDF 各一份。
