# 採購型態與決標方式對文件的影響

本 skill 其餘各檔的預設情境是「**系統開發委外，以公開評選（最有利標）決標**」。實際採購型態不只一種，同樣叫「建議書」，在不同型態下的份量與重點差很多。

> **本檔不引用《政府採購法》條號。** 決標方式與招標程序的法律要件請以招標文件與機關公告為準；本檔只談「文件怎麼寫」的差異。招標文件與本檔說法不一致時，**一律以招標文件為準**。

## 一、先看招標文件的三個欄位

動筆前先在招標公告與投標須知裡找到這三項，它們決定了文件策略：

| 欄位 | 為什麼重要 |
| --- | --- |
| **招標方式** | 公開招標／限制性招標（公開評選）／選擇性招標——決定有沒有評選會議與簡報 |
| **決標方式** | 最有利標／最低標／準用最有利標等——決定建議書是「說服文件」還是「符合性證明文件」 |
| **是否有評選項目與配分表** | 有配分表，建議書章節就依配分表排；沒有，才用通用架構 |

找不到就直接問機關承辦人或看招標文件的問答紀錄，不要用猜的。

## 一之二、「政府資訊服務採購作業指引」對文件的影響

行政院公共工程委員會與數位發展部 112 年 9 月 25 日（工程企字第 1120022701 號）發布的「政府資訊服務採購作業指引」，是現行辦理資訊服務採購的主要依據，分預算編列、廠商資格、需求文件、招決標作業、契約執行、爭議處理六段。與文件撰寫直接相關的幾項：

| 指引要求 | 對文件的意義 |
| --- | --- |
| 按比例編列資安預算並單獨列項 | 建議書的經費配置表要看得出資安項目單獨成列，不要混在系統開發裡 |
| 載明服務水準及資安要求 | SLA 項目參照該指引附件（見 `references/04-履約與維運文件.md` 第五節）；資安要求對應「共通性資通安全基本要求參考一覽表」 |
| 使用政府資料傳輸平臺及納入零信任架構 | 涉及跨機關資料傳輸時，架構圖與介接說明要交代是否走政府資料傳輸平臺；資安章節要回應零信任 |
| 要求廠商投標時載明執行規劃 | 建議書不能只寫「將依機關需求辦理」，要寫出可查核的執行規劃 |
| 評選項目考量廠商資安實績及作為 | 建議書的公司實績章節要單獨呈現資安實績與資安管理作為，不要只列系統開發案例 |
| 反覆檢視需求訪談結果，確認後始進行開發 | 需求訪談紀錄要有機關確認的簽核欄位，這份紀錄是 SRS 附錄的必要內容 |
| 開發過程設定查核點，反覆檢視執行成果 | 專案執行計畫書的查核點要對應可檢視的成果，不能只寫時程百分比 |
| 機關新增需求應合理增加經費及期程 | 需求變更文件要同時評估經費與期程影響，不要只寫技術影響 |
| 機關以取得授權利用為原則 | **著作權歸屬不要預設為「歸屬機關」**，依契約寫；詳見 `../tw-gov-it-review/references/03-法規速查.md` 第五節 |

> 指引屬行政指導，實際要求仍以該案招標文件與契約條文為準。指引與招標文件不一致時，以招標文件為準。

## 二、最有利標與最低標的建議書差異

### （一）最有利標（含公開評選、準用最有利標）

- 有評選委員會、有簡報與答詢。**建議書是評分依據**。
- 章節**依評選項目配分表排列**，並在章名後標註對應項目與配分。詳見 `references/01-建議書.md`。
- 配分高的項目要給足篇幅。配分 30% 的「系統開發能力」寫兩頁、配分 5% 的「公司實績」寫十頁，是明顯的資源配置錯誤。
- 需求回應對照表、人力配置、時程查核點、SLA 承諾都是常見的評分細項。
- 有頁數限制時，優先砍公司簡介與通用技術介紹，不要砍需求回應與專案管理。

### （二）最低標

- 沒有評選會議，**價格決定得標**。但「規格符合」仍是門檻：資格或規格不符會被判定不合格。
- 此時「建議書」的性質接近**規格符合聲明**。重點文件是：
  - **規格符合對照表**：機關規格條文 → 本廠商提供之產品／服務規格 → 佐證文件頁次。逐條對應，一條都不能漏。
  - 資格文件（公司登記、財務、實績、認證）齊備——缺件的後果比寫得不漂亮嚴重得多。
- 寫法上力求**精確、可查證**，不需要說服性的鋪陳。規格若以「或同等品」表示，要一併提出同等品證明與比較表。
- 交付文件的要求則多寫在契約與需求說明書裡，履約階段的文件規格與最有利標案並無二致。

### （三）異質採購最低標與其他變形

有些案子採「先審資格與規格、通過者再比價」的方式。文件策略等同最低標，但技術文件的審查較嚴，等於要用最有利標的態度寫技術規格符合說明、用最低標的態度控制價格。招標文件會寫明審查程序，逐條照做即可。

**通則**：不確定屬於哪一種時，就同時把「規格符合對照表」與「需求回應對照表」都做出來。前者防不合格，後者防低分，成本不高。

## 三、共同供應契約

機關可依已訂定的共同供應契約項下規格逕行採購，不再另行招標。

**特徵與文件影響**

- **沒有建議書、沒有評選。** 機關比較的是契約項下各廠商的品項、規格與價格。
- 廠商端的重點文件是：**品項規格說明**、交貨與安裝時程、保固與維護服務內容、驗收條件。
- 交付文件通常大幅簡化，常見的只有：交貨清單、安裝設定紀錄、教育訓練紀錄、驗收單、保固說明。**不會要求 SRS／SDD 這類開發階段文件**——除非採購標的本身包含客製開發。
- 若採購標的是「軟體授權＋導入服務」，導入服務的部分仍可能要求提出導入計畫、教育訓練與驗收文件，要看契約項下的服務內容說明。

**撰寫要點**

- 規格說明要能逐條對應契約項下的規格欄位，型號、版本、數量、單位一字不差。
- 保固起算時點（到貨日？驗收合格日？）要寫明，這是共同供應契約案最常見的爭議。
- 不要套用開發案的文件架構。機關承辦人拿到一本 SRS 只會覺得你搞錯案子了。

## 四、雲端服務採購（SaaS／PaaS／IaaS）

採購標的從「交付一套系統」變成「訂閱一項服務」，文件的關注點跟著換。

**與自建案的主要差異**

| 面向 | 自建委外 | 雲端服務採購 |
| --- | --- | --- |
| 交付物 | 原始碼、系統、文件 | 服務存取權、組態設定、營運文件 |
| 智財 | 著作財產權多歸屬機關 | 服務本體屬供應商，機關取得使用權；**機關資料所有權須明確歸機關** |
| 文件重點 | SRS／SDD／測試文件 | 服務規格說明、組態與參數設定文件、介接規格、SLA、資料管理與退場計畫 |
| 驗收 | 功能驗收＋文件驗收 | 服務可用性驗證＋組態驗收＋教育訓練 |

**文件中務必涵蓋（機關最常追問的幾項）**

1. **資料落地與所在地**：資料儲存於何處、有無跨境傳輸、備份副本存放位置。機關對此的要求差異很大，一律以招標文件與機關資安規定為準，未確認就寫 `【待填：機關對資料儲存所在地之要求】`。
2. **資料所有權與可攜性**：機關資料的所有權歸屬、機關要求匯出時的格式與時限。
3. **退場（Exit）計畫**：契約終止或不續約時，資料匯出方式與格式、供應商端資料刪除的程序與證明、過渡期間的服務延續安排。**這一節沒寫，機關幾乎一定會要求補。**
4. **服務水準（SLA）**：可用度、故障回應與修復、維護時窗與變更通知期限、未達成的補償方式。格式參考 `references/04-履約與維運文件.md` 第五節。
5. **資安與稽核**：供應商持有的資安認證、機關可否進行稽核或要求稽核報告、事件通報時限與窗口、與機關資安規定的對應說明（見 `../tw-gov-it-review/references/03-法規速查.md`）。
6. **變更管理**：供應商單方面改版、停止功能、調整計價時的通知義務與機關的選擇權。
7. **計費模式**：計價單位（帳號數、用量、儲存容量）、超量計費、契約期間的價格調整條件。用量型計費要在文件中列出用量估算依據，避免決標後爆預算。
8. **個資與委外監督**：若服務涉及處理個資，機關對受託者的監督機制、供應商的再委託（子處理者）揭露與同意程序。

**撰寫要點**

- 不要照抄雲端供應商的英文服務條款當作規格說明。機關要的是「對應到本案需求的中文說明」與「差異之處的因應」。
- 供應商制式 SLA 與機關要求不一致時，據實寫出差異並提出補強方案（如加購支援等級、廠商自行承擔的服務保證），不要含糊帶過。
- 服務本身無法客製時，功能落差要明列並提出替代作法。這比宣稱「完全符合」在履約階段安全得多。

## 五、其他常見型態

| 型態 | 文件重點 |
| --- | --- |
| **開口契約（不定量）** | 契約期間內依機關通知逐案執行。文件重點在：服務項目與單價表、派工與計價方式、每案的工作說明書（SOW）與驗收紀錄、期間彙總報告 |
| **維護服務採購**（既有系統，非新建） | 服務範圍界定（哪些算維護、哪些算新增需求）、現況系統盤點、服務水準、月報格式、知識移轉。範圍界定沒寫清楚是最大的爭議來源 |
| **統包（設計＋施工／建置一併）** | 前期規劃文件的份量加重（需求分析、可行性、整體規劃），且廠商要對整體效能負責，文件中的量化承諾要更保守 |
| **資訊服務人力（駐點）** | 重點在人員資格證明、投入工時計算與簽核、工作紀錄與成果報告。**不要用系統開發案的文件架構**，機關要的是工時與成果的可查核性 |
| **軟體授權採購** | 授權種類與數量、授權範圍（機關全體／指定單位／指定主機）、升級與技術支援期間、原廠證明 |

## 五之二、AI 專案

本案若導入 AI 或生成式 AI，**本 skill 的幾個預設做法會不成立**，動筆前先讀數位發展部「公部門人工智慧應用參考手冊」（114 年 12 月 17 日發布，數位政府司），並確認機關要求依該手冊的哪些章節辦理。

該手冊第 3.7 節「AI 與傳統資訊專案的差異」指出的落差，直接影響文件怎麼寫：

| 手冊指出的差異 | 對文件的影響 |
| --- | --- |
| 專案期程不容易預估與控制，AI 專案多採敏捷開發、短循環迭代 | 甘特圖與查核點不能照傳統瀑布式排。時程要留迭代輪次，查核點綁「完成第 N 輪評估」而非「完成 X% 功能」 |
| 產出是否符合機關期待需仰賴機關與執行團隊討論驗證，生成式 AI 的產出並無標準答案 | 需求追溯鏈的「驗證方式」欄不能只寫「功能測試通過」。要寫評估資料集、評估指標與判定門檻，並載明機關參與驗證的方式 |
| 資料驅動，資料品質管理耗費資源，訓練可能用到機敏資料 | 需求規格書要有資料來源、資料品質標準、訓練資料的使用權限與存放位置，並對應個資與資安章節 |
| 對 AI 技術認知錯誤會帶來不實期望 | 建議書不要寫「AI 將自動完成○○」這類無條件承諾。寫清楚適用範圍、已知限制與人工複核機制 |

驗收標準另依該手冊 3.6 節的「AI 專案驗收標準檢核清單」，其要點包括：選擇**多種指標組合**（模型性能、系統穩定性、使用者體驗、公平性）而非單一指標；生成式 AI 應將回應時間列入標準；設立多元使用者體驗指標；模型性能標準須考量實際應用場景，並確保程式碼、模型文件與 metadata 完備以利後續維護。

**手冊列的是檢核項目，不是數值。** 門檻值一律依機關要求或雙方議定後填入，本 skill 不提供建議值。

**本節止於採購與驗收標準層，文件層未覆蓋。** 各文件骨架仍是傳統資訊專案的欄位，沒有評估資料集與指標、模型卡、訓練資料授權、prompt 與檢索索引交接、模型漂移與再訓練等欄位。要寫這些段落時依通用工程實務撰寫，並在文件中標明該段非依官方規範。**若本案是可自主呼叫工具的 AI agent**，該手冊的範圍是 AI 應用而不含自主代理，權限邊界與工具呼叫稽核軌跡無官方依據可引用。

《行政院及所屬機關（構）使用生成式 AI 參考指引》的限制仍然適用——**機密文書不得使用生成式 AI**，且不得向生成式 AI 提供涉及機密業務或個人資料之訊息。

## 六、快速判斷表

| 招標文件的線索 | 研判型態 | 文件重心 |
| --- | --- | --- |
| 附「評選項目及配分表」、要求簡報 | 最有利標／公開評選 | 建議書依配分表排章，需求回應對照表 |
| 只有規格清單與投標標價清單 | 最低標 | 規格符合對照表、資格文件齊備 |
| 提到「共同供應契約」「契約編號」 | 共同供應契約 | 品項規格、交貨安裝、驗收單 |
| 標的為「訂閱」「服務」「雲端」，以月／年計價 | 雲端服務採購 | SLA、資料所有權與退場計畫 |
| 「依機關需求隨時通知辦理」「單價決標」 | 開口契約 | 單價表、派工與計價、逐案 SOW |
| 標的為「維護」「保修」既有系統 | 維護服務採購 | 服務範圍界定、SLA、月報 |
| 要求交付原始碼、SRS、SDD、測試文件 | 系統開發委外 | 本 skill 其餘各檔的預設情境 |

判斷不出來時，直接問使用者招標文件的「決標方式」與「交付項目說明」怎麼寫，比猜快得多。
