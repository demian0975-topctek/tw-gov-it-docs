# 履約管理、上線與維運階段文件

`references/02-交付文件規格.md` 涵蓋的是開發階段的核心交付物。本檔補上開發前後兩端常被機關列入交付項目、但範本較少的文件：契約與履約管理、資料移轉、上線切換、營運交接，以及進入維護期後的月報與服務水準報表。

> 各機關對這些文件的名稱與要求差異更大（有的併入專案執行計畫書，有的獨立成冊）。**若機關的交付項目說明有列，以機關版本為準**；本檔僅供機關未明訂時使用。

## 一、契約與履約管理文件

這一類文件的用途是「把契約條款落成可執行的動作」。多數不會單獨成冊，而是散在專案執行計畫書、會議紀錄與請款文件中，但驗收與稽核時會被要求提出。

| 文件 | 內容重點 | 產生時機 |
| --- | --- | --- |
| 履約進度報告 | 契約工作項目與實際進度對照、查核點達成情形、逾期項目及原因 | 依契約，多為每月 |
| 需求變更申請單 | 變更編號、提出人、變更內容、影響評估（工時、時程、費用、受影響需求編號與文件）、雙方簽核 | 需求變更時 |
| 履約爭議與展延申請 | 事由、依據（契約條款或機關配合事項未到位之紀錄）、影響天數、佐證文件 | 發生時 |
| 分包管理紀錄 | 分包廠商名稱、分包項目與比例、資格文件、保密切結 | 有分包時 |
| 人員異動紀錄 | 異動人員、原任角色、接替人員資歷、交接內容與日期 | 異動時 |
| 保密與資安切結 | 專案人員名冊、切結書、門禁與帳號申請與註銷紀錄 | 人員進場／離場 |
| 驗收申請與驗收紀錄 | 交付項目清單對照、缺失改善情形、驗收結論 | 各階段驗收 |
| 請款文件 | 依契約付款辦法之階段別、應附之驗收證明與發票 | 各付款階段 |

> **上表中「履約進度報告」「需求變更申請單」「分包管理紀錄」等是廠商內部或雙方往來的管理文件，本 skill 負責。
> 但若機關要求以「函」正式行文（展延申請函、需求變更陳報函、履約爭議函、驗收申請函），公文本體屬公文書，
> 格式依《文書處理手冊》，應交由公文 skill（如 [tw-formal-writing](https://github.com/Imbad0202/tw-formal-writing)）處理；
> 本 skill 只負責函的附件——影響評估表、進度對照表、佐證資料。詳見 `SKILL.md`「這個 skill 不做公文書」一節。**

**撰寫要點**

- **需求變更申請單一定要標「受影響需求編號」。** 這是需求追溯鏈在履約階段的延伸；沒有這一欄，變更後的文件版本就會與追溯表脫勾，驗收時對不起來。
- **機關配合事項要在專案執行計畫書就寫清楚**（測試環境開放、既有系統介接窗口、資料提供、人員受訓時段）。日後展延申請的依據就是這一節加上會議紀錄。
- 逾期項目據實填寫並附因應措施。履約進度報告是機關履約管理的正式紀錄，事後補寫或美化，在稽核時風險更高。

**展延申請要引契約條款，不要只寫「因故延誤」。** 資訊服務採購契約範本（113 年 12 月 26 日修正）第七條（四）1 列出七款「確非可歸責於廠商」而得展延且不計逾期違約金的事由，申請時對號入座並附事證：

| 契約範本第七條（四）1 所列事由 | 常見情境 |
| --- | --- |
| （1）發生契約規定不可抗力之事故 | 事由清單見同條第（六）款十三項 |
| （2）因天候影響無法履約 | |
| （3）機關要求全部或部分暫停履約 | 附機關通知 |
| （4）因辦理契約變更或增加履約標的數量或項目 | 附需求變更申請單 |
| （5）**機關應於一定期間內核定或辦理事項未及時辦妥** | 最常用的一款；需有會議紀錄或往來文件佐證 |
| （6）機關自辦或機關之其他廠商延誤而影響契約進度 | 介接對象未到位屬此 |
| （7）履約標的有不明確之情事且無可歸責於廠商之事由 | 機關需求未定案導致 |

同條並規定：應於事故發生或消失後檢具事證以書面申請；事由未達半日者以半日計，逾半日未達 1 日者以 1 日計。

**逾期違約金與驗收延誤的計算基礎**（第十四條、第十二條（二））：

- 逾期違約金每日按契約價金總額 1‰；未完成部分不影響其他已完成部分之使用者，按未完成部分每日 3‰。總額上限由機關載明，**不高於 20%，未載明者為 20%**。
- 初驗或驗收有瑕疵經通知限期改正者，逾期日數應**扣除**「機關決定限期改正前歸屬於機關的作業日數」與「契約或主驗人指定之限期改正日數」。
- **因可歸責於機關之事由延誤辦理初驗或驗收，該延誤期間不計逾期違約金**；機關因此延遲付款者，遲延利息及廠商增加之延長保證金費用由機關負擔。

這三項是履約爭議時最常被引用的計算依據，進度報告與展延申請的天數要能對上。

## 二、資料移轉計畫與報告

多數機關委外案都涉及既有資料的移入（舊系統、Excel、紙本建檔）。資料移轉常是上線前最容易爆的環節，也是文件最容易寫得空泛的一份。

### 資料移轉計畫

| 章節 | 應涵蓋內容 |
| --- | --- |
| 移轉範圍 | 來源系統與資料集清單（資料表／檔案、筆數概估、負責單位）、不移轉的資料及其理由與後續處理方式 |
| 移轉策略 | 一次性移轉或分批移轉；全量或增量；歷史資料保留年限；移轉期間新舊系統的並行方式 |
| 欄位對應表 | **本計畫的核心。** 來源欄位 → 目標欄位、資料型態與長度轉換、預設值、代碼對照（新舊代碼表）、無對應欄位之處理 |
| 資料清理規則 | 重複資料判定與合併規則、缺漏必填欄位之補值或退件規則、格式錯誤（日期、身分證字號、地址）之修正規則、清理前後皆須留存 |
| 移轉程序 | 前置作業（備份、凍結來源資料異動）、執行步驟與預估時間、負責人、每一步驟的檢核點 |
| 驗證方式 | 筆數比對、關鍵欄位總和比對（金額、數量）、抽樣逐筆比對（抽樣比例與抽樣方法）、業務單位確認機制 |
| 個資保護 | 移轉過程之存放位置與存取權限、加密方式、測試環境之去識別化規則、移轉完成後暫存檔之銷毀程序 |
| 演練規劃 | 至少一次完整演練，含演練時程、資料量、預期耗時；演練發現問題之修正與再演練條件 |
| 回復程序 | 移轉失敗之判定標準、回復到移轉前狀態的步驟與預估時間 |
| 分工與時程 | 機關端、廠商端、舊系統維護廠商各自的工作與時點 |

### 資料移轉報告

移轉執行後提出，內容為：實際執行時間與耗時、各資料集移轉筆數（來源筆數／成功筆數／失敗筆數／失敗原因分類）、驗證結果（筆數比對、總和比對、抽樣比對之結果數值）、未移轉或人工處理的資料清單與後續處理、業務單位確認簽核。

**撰寫要點**

- **欄位對應表不能只寫「一對一對應」。** 舊系統常有一欄塞多種意義、代碼未標準化、必填欄位實際為空等狀況。對應表要逐欄列，找不到對應就寫 `【待填：來源欄位待機關確認】`，不要假設。
- **驗證方式要能量化。** 「確認資料正確」不是驗證方式；「筆數比對誤差為 0、金額欄位總和比對誤差為 0、抽樣 5% 逐筆比對無差異」才是。
- 資料量大時，先在計畫書載明預估耗時，並確認機關可接受的服務中斷時窗。這一項與上線切換計畫要對得起來。
- 移轉涉及真實個資，測試與演練所用資料的去識別化規則須明確；相關規劃對應 `../tw-gov-it-review/references/03-法規速查.md` 第四節。

## 三、系統上線切換計畫

上線切換計畫是給機關長官與資訊單位看的「當天怎麼做、出事怎麼辦」。寫得好不好，看的是**回復程序寫不寫得出來**。

| 章節 | 應涵蓋內容 |
| --- | --- |
| 上線範圍與方式 | 上線功能範圍；切換方式（一次全面切換、分階段上線、新舊並行）及選擇理由 |
| 上線前準備 | 正式環境建置與組態確認、憑證與網域設定、資安檢測完成證明、無障礙檢測結果、教育訓練辦理完成、使用手冊交付、客服窗口開通 |
| 上線檢核表 | 逐項可勾選的檢核清單，每項註明負責人與完成判定方式 |
| 切換時程表 | 以「時：分」為單位的當日時程：服務公告、舊系統停止異動、資料最終同步、系統部署、冒煙測試、開放服務。每一時點標註負責人與預估耗時 |
| 服務中斷公告 | 公告管道、公告時點（提前天數）、公告內容範例、對外客服說明稿 |
| 冒煙測試項目 | 上線後立即執行的最小驗證集（登入、關鍵交易、報表、介接、通知發送），每項註明預期結果 |
| 回復（Rollback）程序 | **回復判定標準**（什麼情況決定回退，由誰決定）、回復步驟、預估回復時間、回復後的對外說明 |
| 上線後觀察期 | 觀察期長度、加強監控項目與門檻值、駐點或待命人力安排、問題回報與處理流程、每日狀況回報機制 |
| 分工與聯絡表 | 機關端、廠商端、機房或雲端服務窗口之姓名與聯絡方式（**實際聯絡資料由承辦人填寫**，文件中留 `【待填】`） |

**撰寫要點**

- **回復判定標準要事先寫死。** 上線當天再討論「要不要退」一定來不及。寫法例如：「冒煙測試關鍵項目任一項失敗，且於 `【待填：分鐘數】` 分鐘內無法排除者，由機關資訊單位主管決定執行回復。」
- 切換時程表要留緩衝。實務上部署與資料同步的耗時常被低估，時程表排得剛好，等於沒有排。
- 觀察期的監控門檻要與 SRS 的非功能需求一致（回應時間、錯誤率、可用度），不要另立一套數字。

## 四、營運交接文件

保固或維護期結束、或改由機關自行維運、或換手給後續廠商時提出。機關最在意的是：廠商離場後，接手的人接不接得住。

| 章節 | 應涵蓋內容 |
| --- | --- |
| 交接標的清單 | 系統與模組清單、原始程式碼與版本、建置與部署腳本、設定檔（敏感值遮蔽並註明由誰保管）、文件清單與版本、資料庫結構與資料 |
| 帳號與權限交接 | 各類管理帳號的用途與保管方式、交接後應辦理的密碼變更與帳號註銷清單、憑證與金鑰的保管與到期日 |
| 環境與資產 | 伺服器、網路、雲端資源、授權（軟體授權、憑證、第三方服務訂閱）之清單、到期日與續約窗口 |
| 維運知識 | 系統架構說明、日常維運作業（備份、監控、批次排程）、常見故障與處理方式、已知限制與技術債、待辦事項清單 |
| 教育訓練 | 向接手單位或廠商辦理之交接訓練場次、教材、參與人員 |
| 未結案項目 | 未修正缺失、進行中的需求變更、待機關決策事項，各附現況與建議處理方式 |
| 交接會議與簽收 | 交接會議紀錄、交接清單逐項簽收、雙方簽章 |

**撰寫要點**

- **授權與憑證到期日一定要列表。** 交接後最常出事的就是沒人知道某張憑證何時到期。
- 「已知限制與技術債」誠實寫。接手方遲早會發現，事先寫明反而是專業表現。
- 敏感值（密碼、金鑰、連線字串）不寫入交接文件本文，改以「保管方式與交付程序」描述，實際值由雙方以另行約定的安全方式交付。此節對應 `../tw-gov-it-review/references/03-法規速查.md` 第六節。

## 五、維護階段月報與服務水準報表

保固期或維護契約期間的例行文件。份量不大，但**格式一旦定案就要每月一致**，機關會拿前後月比較。

### 維護月報

| 章節 | 應涵蓋內容 |
| --- | --- |
| 本月摘要 | 系統運作概況、重大事件、需機關決策事項 |
| 服務水準達成情形 | 對照契約 SLA 逐項填列（見下表） |
| 案件統計 | 本月受理案件數，依類別（故障、諮詢、資料處理、需求調整）與嚴重等級分類；開立、結案、未結案件數 |
| 案件明細 | 案件編號、受理時間、類別、等級、內容摘要、處理方式、回應時間、修復時間、結案時間、狀態 |
| 未結案件 | 逐案說明現況、卡在哪裡、預計完成時間 |
| 系統效能與可用度 | 可用度統計（含計畫性維護扣除說明）、回應時間統計、資源使用率趨勢 |
| 資安事項 | 弱點通告因應情形、修補套用紀錄、第三方元件版本更新、異常存取紀錄 |
| 備份與還原 | 備份執行狀況、還原演練辦理情形 |
| 下月工作規劃 | 預定辦理事項與需機關配合事項 |

### 服務水準（SLA）報表

**訂 SLA 項目時的官方參考來源**：「政府資訊服務採購作業指引」（112 年 9 月 25 日，行政院公共工程委員會與數位發展部）附件「常用資訊服務等級協議（SLA）之參考項目」。該附件把常用指標分成三大類，並標示每一項適用於**規劃／設計／建置／維運**哪些階段、以及適用軟體或硬體：

| 大類 | 子類 | 該附件列的指標舉例 |
| --- | --- | --- |
| 一、系統及服務可用性 | 環境面 | 服務韌性（電力、水、網路、空調、濕度調節之備援）、對外網路環境中斷累計時間 |
| | 服務面 | 服務可用性（Service Availability）、正常運行時間百分比、MTBF、MTTR、系統穩定度、反應時間、批次作業時間、檔案傳輸時間、滿意度調查 |
| | 永續維運與管理 | 營運異地備份／備援、RTO、RPO、最大可忍受中斷時間（MTPD）、備品供應、HA 切換演練 |
| | 資通安全品質 | 風險評鑑與風險管理計畫、實體及遠端登錄管制與稽核、漏洞修補、資通安全政策執行品質、資安測試之改善、安全防護計畫執行、資安事件之通報及應變、調查及處理資安事件之時效、外部稽核 |
| 二、廠商之服務品質 | 設計與開發階段等 | 未依機關同意之流程或設計準則開發之比率、未依限回應問題之次數 |
| 三、使用者體驗 | | 依該附件所列項目選用 |

該附件明言「機關可依個別系統之類型、重要性、複雜性、機敏性及使用情境**選用**項目」，並非全部都要訂。附件內的數值一律留空白（如「不得超過 ____ 小時」），**沒有建議值**——本 skill 同樣不提供建議值。

契約若訂有 SLA，月報須逐項對照。表格範例：

**撰寫要點**

- **回應時間與修復時間要分開計算**，且要定義「起算時點」（機關通報時間？系統告警時間？）。沒有定義起算點的 SLA 在爭議時完全沒用。
- **可用度的計算方式要寫明**：分母是全月時間還是服務時段、計畫性維護扣不扣除、扣除的條件（提前幾日公告）。這是月報最常被質疑的一欄。
- 未達成時不要只寫「因不可抗力」。寫清楚事件經過、影響範圍、已採取的改善措施與預防再發生的作法。
- 案件明細表的欄位一經確定就固定下來，方便機關逐月彙整與年度統計。
