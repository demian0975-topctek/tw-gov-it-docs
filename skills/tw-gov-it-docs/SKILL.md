# 台灣政府資訊系統委外文件撰寫

協助廠商（或機關承辦人）產出符合台灣公部門審查與驗收慣例的資訊系統開發文件。

這類文件的評分者不是工程師，而是評選委員與驗收小組。他們看的是「有沒有對應到需求說明書的每一條」「章節有沒有齊全」「有沒有可查核的量化承諾」。因此本 skill 的核心不是把文件寫得漂亮，而是把**可追溯性**與**章節完整性**做到位。

## 開始前先確認的事

不要在資訊不足時憑空生成。動筆前先向使用者確認以下項目，缺的就問，問完再寫：

1. **文件類型**：發包階段（機關端工作說明書）、投標階段（服務建議書）、履約階段（交付文件），還是上線與維運階段（資料移轉、上線切換、交接、月報）？是哪一份？
2. **採購型態與決標方式**：系統開發委外、共同供應契約、雲端服務採購、開口契約還是維護服務？最有利標還是最低標？**這一項決定文件的性質**（說服文件 vs 規格符合證明），判斷方式見 `references/05-採購型態.md`。
3. **機關與案名**：全銜、案名、預算金額級距、履約期限。
4. **來源文件**：有沒有機關的「需求說明書」或「建議書徵求文件（RFP）」？**這份是最重要的輸入。** 有的話請使用者貼上或上傳，全文的章節與需求編號要作為撰寫骨架。
5. **評選項目與配分**（僅最有利標的建議書需要）：RFP 通常附有評選項目表，建議書的章節必須一比一對應配分項目。
6. **既有範例**：使用者公司過去驗收通過的同類文件。有的話優先模仿其章節編號、用語、表格樣式。

若使用者沒有 RFP，就依 `references/02-交付文件規格.md` 的標準章節架構產出，並在文件開頭標註「本版依通用架構撰寫，收到機關需求說明書後須逐條校對」。

**使用者角色**：本 skill 同時適用投標廠商與機關承辦人。廠商端重點在得分與不被退件；機關端重點在需求寫得判不判得出合格、交付項目的訂定與驗收檢核。**兩者的措辭與立場不同，不確定時先問一句。** 機關端要從頭寫工作說明書（需求說明書、RFP）時，走 `references/07-機關端工作說明書.md` 與 `assets/13-工作說明書骨架.md`；其餘各檔的預設立場都是廠商端。

**使用者是受機關委託協助撰寫的顧問（機關本身不熟悉技術）時，改用 `tw-gov-ta-docs`**——那是獨立的 skill，處理的是顧問手上沒有機關內部事實（預算、既有系統、內部簽核期程）卻要交出精確文件的訪談與交接問題，骨架與判準自成一套，不跟本 skill 共用。

## 撰寫流程

**第一步：接上追溯鏈的第一環。**
在寫任何內容之前，先把 RFP 或需求說明書的每一項需求編號化（R-001、R-002…）。**機關端是在工作說明書裡建立這一環，廠商端是接上它**；機關已編號時，廠商沿用機關的編號，不另編一套。整組文件靠這條鏈串起來：

```
RFP 需求編號 → 軟體需求 → 設計元件 → 驗證方式 → 單元測試案例 → 整合測試案例
```

建議書用它證明「每條都回應了」，需求規格書用它當需求追溯表的左欄，測試文件用它對應測試案例編號。**後面每寫一個欄位，都要問這個欄位掛回鏈上的哪一環**；掛不上去的欄位不是不重要，是位置放錯了。這一步做對，後面的文件自然一致；跳過這一步，文件之間一定對不起來。

**第二步：搭章節骨架，先不填內容。**
把完整目錄列給使用者確認。章節缺漏在驗收時是硬傷，比內容寫得普通嚴重得多。

**機關版本一律優先。** `references/02-交付文件規格.md` 與 `assets/` 的章節是通用底稿，不是強制規範；使用者手上有機關的「交付項目文件說明」附件時，以機關的章節名稱與順序為準，一字不改，本 skill 的規格只用來補機關沒列到的部分。

**第三步：逐章撰寫。**
- 動筆前先看 `references/03-範例集.md` 的對應範例，確認顆粒度。
- 已知事實照實寫。
- 使用者未提供的具體資訊（人名、期程、金額、機關內部環境），用 `【待填：○○】` 明確標示，**不要編造**。編造的技術細節在審查會上會被當場問倒。
- 承諾要可量化、可查核：「系統回應時間 3 秒內（95 百分位）」優於「系統效能良好」。
- 引用法規前，先對照 `../tw-gov-it-review/references/03-法規速查.md` 的法規速查表。**未經查證的法規條號一律不寫**，只寫法規全名。

**第四步：交給 `tw-gov-it-review` 審一遍。**
草稿寫完就換位置，用審查的眼光跑一次結構、用語、法規三道檢查，把會被退件的項目改掉再交給使用者。自己寫自己審容易漏，寧可多跑一次。機關端的工作說明書改跑 `../tw-gov-it-review/references/01-結構與格式.md` 第九節的機關端檢核清單——那裡問的是「廠商看不看得懂、驗收判不判得出來」，不是「會不會被退件」。

**第五步：附上待確認事項清單。**
不要把 `【待填】` 散在文件裡讓使用者自己找。另附一張表列出：待確認事項、出現位置、要問誰、不確認的影響。格式見 `references/03-範例集.md` 第四節。

## 產出格式

- 預設輸出 Markdown，章節用中文數字階層（壹、一、（一）、1.、(1)）。**這五層是計畫書與報告的慣例，不是《文書處理手冊》的公文分項標號**（那是四層，且全半形另有規定，見 `references/06-Word範本.md` 第三節）。
- 使用者要求 Word 檔時，讀 `references/06-Word範本.md`（空白範本與已填好內容的文件走不同路徑，版面規格與 ODF 交付規定也在該檔）。
- 表格能用表格就用表格。公部門審查偏好表格化的規格、時程、對照關係。
- 每份文件都應有：封面（案名、機關、廠商、版本、日期）、文件版本紀錄表、目錄。

## 這個 skill 不做公文書

判斷準則：**這份文件會不會用機關發文字號發出去？** 會，就是公文書（函、令、公告、開會通知單，以及存證信函、契約、陳情書），體例依《文書處理手冊》，交給公文 skill（如 [tw-formal-writing](https://github.com/Imbad0202/tw-formal-writing)）。

履約期間行文給機關（展延申請、需求變更陳報、履約爭議、驗收申請）時，**公文本體交給公文 skill，本 skill 負責附件的技術內容。**

機關端同理：招標文件裡本 skill 只做**工作說明書**這一份技術文件。投標須知、廠商資格、契約條款由機關的採購或總務單位依範本產生，本 skill 只負責檢查它們與工作說明書有沒有矛盾（見 `references/07-機關端工作說明書.md` 第九節）。

技術文件用第三人稱敘述體：SRS、SDD、測試文件不帶稱謂語（鈞、貴）與主旨／說明結構；建議書因帶行文性質可適度用「貴機關」。  <!-- 檢查略過 -->

## 已知未覆蓋的範圍

章節規格與 `assets/` 骨架**以網站型資訊系統為預設**。碰到下列兩種案子，先告訴使用者這一段沒有現成依據，再依通用工程實務撰寫，並在文件中標明該段非依官方規範：

- **行動應用（App）**：資安與無障礙法規有（見 `../tw-gov-it-review/references/03-法規速查.md`），交付文件的差異沒有——雙平台版本、上架審查期程、公務機與 MDM 派送、推播與離線、第三方 SDK 清單皆未納入。上線切換的限制見 `assets/10-上線切換計畫骨架.md` 開頭。
- **AI 專案與 AI agent**：只覆蓋到採購與驗收標準層，缺什麼、以及哪些部分連官方依據都沒有，見 `references/05-採購型態.md` 第五之二節末段。

## 重要提醒

**依《行政院及所屬機關（構）使用生成式 AI 參考指引》，機密文書應由承辦人親自撰寫。** 標案文件常含機關內網架構、IP 配置、資安設定、系統帳號規劃等敏感內容。撰寫時提醒使用者：勿輸入機關未同意公開的網路架構、實際 IP、帳號密碼原則細節；這些欄位一律留 `【待填】`，由承辦人自行補上。

敏感度最高的是**系統管理手冊**與**營運交接文件**（帳號、金鑰、憑證、開放埠）。這兩份的敏感欄位只記錄「用途與保管方式」，實際值由雙方另行以安全方式交付。

本 skill 產出的是初稿。正式送件前仍須經廠商內部覆核與機關承辦人確認，AI 不取代投標與履約的正式程序。
