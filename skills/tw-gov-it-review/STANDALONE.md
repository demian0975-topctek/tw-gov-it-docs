# 政府資訊系統委外文件審查

審查者的角色不是校稿，是**預測退件**。每一項發現都要能回答一句話：**這一項會不會讓機關把文件退回來？**

- 會 → `[退件]`，交件前必改。
- 不會，但會讓委員扣分或在審查會上被問 → `[建議]`。

分不出來就當作 `[建議]`，不要把兩者混在一起講——使用者需要知道哪些非改不可。

## 開始前先確認的事

1. **這是哪一份文件？** 建議書、SRS、SDD、測試文件、手冊、報告、移轉計畫、月報，各自的必備章節不同。**機關端自己寫的工作說明書（需求說明書、RFP）走另一條路**：第一道改用 `references/01-結構與格式.md` 第九節，第二、三道照跑。
2. **有沒有機關的「交付項目文件說明」附件或需求說明書？** 有的話**一律以機關版本為準**——本 skill 的章節規格只是通用底稿，機關要的章節名稱一字不改，機關沒要求的不算缺失。
3. **要審哪一類？** 使用者沒說就兩類都審。

## 三道檢查

**第一道：結構與格式。** 讀 `references/01-結構與格式.md`，逐項對照章節完整性、追溯鏈、階層編號、版面與檔案格式（ODF／PDF）、圖表、合規章節有沒有到位、跨文件一致性、敏感欄位有沒有被寫進去。
完成準則：該檔的檢核清單**每一項都有結論**（通過／不通過／不適用），不通過的都指出在哪一節、缺什麼。

**第二道：用詞用語與表達。** 草稿是檔案就先跑腳本：

```bash
python scripts/check_wording.py 草稿.md
```

`--只看錯誤` 只列必改項並以離開碼回報，`--rules` 列出目前載入的規則。腳本抓的是機械性錯誤，抓到的都是明確會扣分的項目；語意的部分讀 `references/02-用語與表達.md` 人工判斷。

腳本輸出的 [錯誤] 對應 `[退件]`，[建議] 對應 `[建議]`。另有一批**刻意不自動攔**的字（紀錄／記錄、計畫／計劃、臺／台、程序、登錄、界面），判斷方式見該檔的兩張人工判斷表，改之前先確認詞性與對象——自動改一定會錯。

沒有檔案可跑時（在 ChatGPT 或 Gemini 上用單檔版），依該檔的五張【檢查規則】表格人工逐項比對。
完成準則：腳本的 [錯誤] 全部有處置建議，且該檔檢核清單每一項都有結論。

**第三道：法規名稱。** 讀 `references/03-法規速查.md`，把文件裡出現的每一個法規、規範、指引名稱與速查表比對。
**「資訊系統分級與資安防護基準作業規定」「網站無障礙規範 2.0 版」，以及把網站無障礙寫成國家通訊傳播委員會主管，這三項一出現就是 `[退件]`。**  <!-- 檢查略過 -->
未經查證的法規條號一律列為問題，建議只留法規全名。

速查表寫出版本號的項目（範本、手冊、指引），**引用前先確認該版本仍為現行**——投標須知範本一年改版數次。有網路時跑：

```bash
python scripts/check_sources.py --只看異動
```

出現 `[異動]` 表示官方頁面已有更新版本，該版本號在審查報告中不可引用，處理方式與來源清單見 `references/04-來源與查證.md`。
完成準則：文件中所有法規名稱都比對過，逐一有結論。

## 出審查報告

按嚴重度排，不要按文件順序排——使用者要先知道哪些會被退。

| 等級 | 位置 | 問題 | 建議改法 |
| --- | --- | --- | --- |
| `[退件]` | 第參章之三 | 引用「網站無障礙規範 2.0 版」，該名稱已於 110 年 7 月 1 日停止適用 | 改為「網站無障礙規範」 |  <!-- 檢查略過 -->
| `[建議]` | 第肆章之二 | 「儘速修復」無法驗收 | 寫出時限，例如「於通報後 4 小時內完成修復」 |  <!-- 檢查略過 -->

報告要能讓使用者直接改，所以：

- 位置指到章節或行號，不要只說「文中多處」。
- 建議改法要寫出改成什麼，不要只說「建議修正」。
- 同一類問題出現多次，合併成一列並列出全部位置。
- 最後附一張 `【待填】` 清單：出現位置、要問誰、不確認的影響。

## 這幾項不要自己動手改

- **未知資訊一律以 `【待填：○○】` 標示，不得代為編造技術數據、法規條號、人名、機關內部環境資訊。** 審查時發現這類編造內容，列為 `[退件]`，並建議改回 `【待填】`。  <!-- 檢查略過 -->
- **依《行政院及所屬機關（構）使用生成式 AI 參考指引》，機密文書應由承辦人親自撰寫。** 文件若已寫入真實 IP、實際網路架構、帳號與密碼原則細節、資安設定值、開放埠清單，列為 `[退件]`，建議改回 `【待填】` 由承辦人自行補上。系統管理手冊與營運交接文件敏感度最高。
- **機關版本一律優先。** 本 skill 的章節規格與用字規則是通用底稿；與機關的交付項目說明附件不一致時，以機關版本為準，不要拿本 skill 的規格去否定機關的要求。

## 範圍界線

只審**技術文件**。公文書（函、令、公告、開會通知單）與存證信函、陳情書、契約屬另一套體例，交給公文 skill（如 [tw-formal-writing](https://github.com/Imbad0202/tw-formal-writing)）。判斷準則：**這份文件會不會用機關發文字號發出去？** 會，就是公文書。

要從頭寫一份文件、要章節骨架、要 Word 空白範本、要填寫範例，用 `tw-gov-it-docs`。

本 skill 產出的是審查意見，不取代廠商內部覆核與機關承辦人確認。


# 結構與格式審查

審的是**看得見的骨架**：章節有沒有缺、編號對不對、圖表有沒有掛上、追溯鏈接不接得起來。
這一類問題不需要讀懂內容就能判斷，也是驗收時最先被抓的。**缺章節比內容普通嚴重得多。**

## 一、章節完整性

判斷順序有先後，不要顛倒：

1. **機關的「交付項目文件說明」附件**——有這份就以它為準，逐項打勾，機關要的章節名稱一字不改。
2. 沒有機關版本時，才用 `../tw-gov-it-docs/references/02-交付文件規格.md` 的通用章節規格對照。

通用規格是底稿，不是規範。文件多了機關沒要求的章節不算缺失；**少了機關要求的章節就是退件**。

**通用規格以網站型系統為預設，未覆蓋行動應用（App）與 AI 專案。** 審這兩類文件時，只審通用章節與追溯鏈，不要拿通用規格判定 App 或 AI 專屬章節缺漏——缺什麼沒有依據，判了就是誤報。改為向使用者說明這一段需依機關要求自行確認。

各文件的必備段落（不分機關版本，缺了都會被問）：

| 段落 | 說明 |
| --- | --- |
| 封面 | 案名、機關全銜、廠商全銜、文件名稱、版本、日期 |
| 文件版本紀錄表 | 版本、日期、修訂人、修訂內容摘要。版本編號不得跳號 |
| 目錄 | 含圖目錄、表目錄；頁碼須與內文一致 |
| 名詞對照表 | 全案共用一份，避免同一功能在不同文件叫不同名字 |

## 二、追溯鏈

這是本組文件的骨幹，也是審查的重點。五段任一段斷掉，整條鏈就失效：

```
RFP 需求編號 → 軟體需求 → 設計元件 → 驗證方式 → 單元測試案例 → 整合測試案例
```

審查方式：

- 取需求追溯表，確認**每一條 RFP 需求都出現在左欄**，沒有需求被漏掉。
- 反向抽驗：任取一個測試案例編號，往回追到需求編號，中間不能斷。
- 代號體系是否全案一致（需求、元件、介面、報表、程式、資料表各有前綴，且不混用）。
- 需求增刪後追溯表有沒有跟著更新——這是最常見的斷點。

追溯表對不起來時，指出**斷在哪一段**，不要只說「追溯性不足」。

## 三、階層編號

計畫書與報告的慣例是五層：

```
壹、貳、參、肆…        （章）
一、二、三…            （節）
（一）（二）（三）…     （項）
1. 2. 3.               （目）
(1) (2) (3)            （細目）
```

- 正文用中文階層，技術附錄可用 1.1.1 這類阿拉伯數字多層編號。
- 階層不得跳階（壹之下直接出現「（一）」）。
- 同一層級的編號樣式全文一致。

**這五層不是《文書處理手冊》的規定。** 手冊的公文分項標號只有四層——一、／(一)／１、／(１)——**沒有「壹、」**。技術文件用五層沒問題，但文件裡若寫「依《文書處理手冊》之分項標號」而實際用五層，那句依據本身是錯的，列為 `[建議]`：改寫成計畫書慣例，或把依據刪掉。

**機關要求比照公文分項標號時**，手冊第十六點（四）另定全形半形：

| 位置 | 數字 | 括號 |
| --- | --- | --- |
| **分項標號** | 全形（`１、` `２、`） | **半形** `(1)` |
| **內文** | 半形（`3 秒`、`99.5%`） | 中文內容用全形（），純英數內容可用半形 |

**最容易看漏的是「標號用全形、內文用半形，而標號的括號又是半形」**——抄公文範例時常把內文數字一起變成全形。內文的全形英數字本身即為錯誤，`scripts/check_wording.py` 抓得到；標號那一層要人工看。

## 四、版面與檔案格式

**先分清楚哪一層規範真的管得到這份文件。** 最常見的誤判是拿管公文的規範去退技術文件，或反過來以為技術文件不受任何格式拘束：

| 規範 | 對技術文件的效力 | 判為問題的門檻 |
| --- | --- | --- |
| **ODF-CNS 15251 實施計畫**（數位發展部） | **直接適用**：「採購招標文件」明列在政府檔案文件流通範圍內 | 機關要 ODF 而交 `.docx`：`[退件]` |
| **政府文書格式參考規範**（國發會 105.4.1） | **不直接適用**，範圍明文限公文與證書獎狀 | 機關未要求比照公文格式時，版面數值最多 `[建議]` |
| **《文書處理手冊》**（行政院） | **不直接適用**，但用字、標點、數字三項機關普遍要求比照 | 見 `references/02-用語與表達.md` |

**判斷順序：招標文件與契約 → 機關提供的範本 → 上表。** 前兩者有寫就照前兩者；機關給了範本卻沒照範本做，一律 `[退件]`，不必再論規範怎麼寫。

### 檔案格式

「政府文件標準格式（ODF-CNS 15251）實施計畫」把**採購招標文件**列入政府檔案文件流通範圍：**可編輯者以 ODF 為原則（`.odt`／`.ods`／`.odp`），非可編輯者採 PDF。** 這是三套規範裡唯一直接管到標案文件的一條。

- 契約或招標文件明定 `.docx` 者從契約——ODF 實施計畫是行政計畫，招標文件與契約的約定優先。
- **改副檔名不是 ODF。** `.docx` 直接改名成 `.odt` 交出去，機關端檢測工具驗得出來，列為 `[退件]`。
- **Word 轉 ODF 會掉東西**：自動目錄、交互參照、部分表格樣式、頁首頁尾功能變數最常失真。審 ODF 檔時**目錄與標號要逐頁看過**——目錄空白、頁碼全是 1、標號跑掉，都是轉檔後沒複查的典型跡象。

### 版面（機關要求比照公文格式時才是必改）

依「政府文書格式參考規範」（國家發展委員會，105 年 4 月 1 日院授發檔（資）字第 1050008178 號函修正）第四點：

| 項目 | 規範所定 | 審查時看什麼 |
| --- | --- | --- |
| 紙張尺度 | **A4**（21.0×29.7 公分） | 檔案由程式或英文版工具產生時預設常是 Letter（21.6×27.9 公分），沒改就不是 A4 |
| 四邊邊界 | 各 2.5 公分 ± 0.3 公分（即 2.2～2.8） | **Word 預設的左右 3.17 公分超出範圍** |
| 裝訂線 | 至左緣保留 1.5 公分 ± 0.3 公分 | 需裝訂成冊者才看 |
| 字型 | 中文楷書；英文及阿拉伯數字 Times New Roman | 全文一致 |
| 行距 | 12 點字→行距 15 點 ± 3 點（10 點字→10±3；16 點字→28±4；20 點字→36±5） | |
| 書寫方式 | 由左而右、由上而下橫書 | |

該規範自留調整餘地（「因版面之限制需調整者，由各機關自訂之」），所以**版面數值一律最多列 `[建議]`，除非機關的招標文件或範本明文規定**。完整條文、適用範圍與產生合規 Word 空白範本的方式見 `../tw-gov-it-docs/references/06-Word範本.md`。

## 五、圖表

- 每張圖表都要有編號、標題，並在正文中被引用（「詳如圖 3-1」）。**孤立的圖表一定會被問。**
- 圖表編號用「圖 3-1」「表 3-1」（章-序），全文一致。
- 系統架構圖至少三張：整體架構圖、網路架構圖、資料流圖。
- 甘特圖要標出查核點與交付物，橫軸與履約期限對齊。
- 螢幕截圖清晰，敏感資料須遮蔽。

## 六、合規章節有沒有到位

這一節審的是「**該有的合規段落在不在**」，內容正不正確見 `references/03-法規速查.md`。

| 章節 | 缺了會怎樣 |
| --- | --- |
| 系統防護需求分級判定（普／中／高）與四面向評估理由 | 資安章節的地基，缺了後面整段沒有依據 |
| 安全需求對照表（依「資通系統防護基準」七構面編排） | 委員無法逐項對照 |
| 日誌紀錄規劃（四要素） | 驗收必查 |
| 第三方元件清單 | 漏洞追蹤無從談起 |
| 檢測規劃（原始碼掃描、弱點掃描、滲透測試） | 時程表若沒納入，驗收前才做來不及 |
| 無障礙等級、檢測時點與標章申請時程 | 標章審核需作業時間，壓在驗收前一週就是風險 |
| 個資處理（項目、目的、保存期限、去識別化） | |
| 原始碼交付範圍與智財歸屬、開源授權相容性 | |

## 七、一致性

跨文件的對照，單看一份文件看不出來，要並排比：

- 功能名稱一致（SRS 叫「案件管理」，SDD 不能叫「案件維護」）。
- 代號體系一致。
- 清單筆數與明細筆數相符。
- 機關名稱、案名全文正確，**無沿用他案殘留**——這是最傷信任的錯誤，交件前全文搜尋確認。
- 目錄頁碼與內文一致（改完內容忘記更新目錄是最常見的退件原因）。

## 八、敏感欄位該留白的有沒有留白

依《行政院及所屬機關（構）使用生成式 AI 參考指引》，**機密文書應由承辦人親自撰寫**。審查時要反過來確認「不該寫的有沒有被寫進去」：

- 真實 IP、實際網路架構、帳號與密碼原則細節、資安設定值、開放埠清單。
- 截圖是否已遮蔽敏感資料。
- 系統管理手冊與營運交接文件敏感度最高：這兩份的敏感欄位只應記錄「用途與保管方式」，實際值由雙方另行以安全方式交付。

發現這類內容寫進去了，列為**退件等級**，並建議改回 `【待填：○○】` 由承辦人自行補上。

## 九、審的是機關自己寫的 RFP 時

機關承辦人也會拿需求說明書或建議書徵求文件來審。政府資訊委外服務團依實際受理的機關諮詢案件，歸納出 7 項常見問題（《政府機關資訊通報》第 325 期，103 年 11 月），可以直接當檢查項目：

| 常見問題 | 審查時看什麼 |
| --- | --- |
| 需求規格不明確或不合理 | 文字是否籠統到機關與廠商日後會解讀不一；是否僅就現有廠商所提建議改寫（有綁標之虞） |
| 專案管理規範不足 | 有無要求廠商的專案管理計畫涵蓋專案組織、工作流程與查核點、定期工作報告與會議、風險與變更管理、品質管理、測試驗收計畫 |
| 服務水準（SLA）要求不合理 | 過嚴會導致廠商必然違約，過寬則上線後效能不彰；項目選用見 `../tw-gov-it-docs/references/04-履約與維運文件.md` 第五節 |
| 文件品質不佳或架構缺乏整體性 | 結構是否鬆散、重要需求項目遺漏或重複描述、前後矛盾 |
| 現行資訊作業環境未適當描述 | 投標廠商不清楚機關環境，描述過簡會讓廠商無法正確評估投入資源 |
| RFP 內容與契約書條文無法適當匹配 | 招標須知與契約書多由總務單位統一制訂，RFP 由資訊承辦人研擬，兩者容易矛盾 |  <!-- 檢查略過 -->
| 需求項目超出預算金額 | 需求規格明顯超出預算會使優良廠商不願投標 |

該文另提供「RFP 內容大綱撰寫建議」，分七章：專案概述、現況及問題說明、專案工作需求、專案管理需求、驗收與付款、建議書製作規定、評選作業，並依專案規模標示各節為必要或視需要。**該文為 103 年資料，其自訂的專案規模金額分級不是現行法定門檻**，章節結構可參考，金額級距請改依現行採購規定與「政府資訊服務採購經費估算編列手冊」。

### 章節完整性

對照 `../tw-gov-it-docs/assets/13-工作說明書骨架.md` 逐章核對。**機關已有自訂格式時以機關版本為準**，該骨架只用來補機關沒列到的章節。最常缺的四項：

| 常缺章節 | 不寫的後果 |
| --- | --- |
| **不屬本案範圍之項目** | 履約期間對「這算不算本案該做的」各說各話 |
| 現行資訊作業環境 | 廠商無法估算投入資源，投標價格失真 |
| 逐條的驗收標準與合格判準 | 驗收時無從判定合格，只能由雙方協商 |
| 機關可提供之資源與配合事項 | 廠商的期程規劃缺一段，延誤責任歸屬不清 |

### 需求判不判得出合格

逐條讀功能需求與非功能需求，問一句：**兩個不認識的人照這條做，會不會做出不同的東西？**

只有形容詞、沒有數量／時點／格式／對象／失敗處理的條文，列為 `[退件]`。好壞寫法對照見 `../tw-gov-it-docs/references/07-機關端工作說明書.md` 第三節。

「依機關屆時指定之方式辦理」這類把未定事項寫成廠商義務的條文，同樣列為 `[退件]`——廠商無法估價。

### 追溯鏈的起點

機關端的追溯鏈從工作說明書起算，不從建議書起算：

- 需求有沒有編號？沒有編號，各廠商會各編各的，決標後要重編一次。
- **每個需求編號在驗收標準表都有對應列嗎？** 對不上的需求無法驗收，逐一列出編號。
- 交付文件表列的每份文件，都有交付時點與審查方式嗎？

### 綁標之虞

- 硬性規格中有指定品牌或型號而未載明「或同等品」及其認定方式者，列為 `[退件]`。
- 規格組合明顯來自單一產品型錄、或與現有廠商既有系統高度一致者，列為 `[建議]`並指出是哪幾條。

### 與投標須知、契約條款的匹配

這是常見問題表第 6 項的具體查法。**優先順序不是慣例，是契約寫的**：資訊服務採購契約範本（113.12.26 修正）第一條（三）1「招標文件內之投標須知及契約條款優於招標文件內之其他文件所附記之條款」——工作說明書屬「其他文件」，不一致時**以契約條款為準**，建議修改工作說明書。

逐項比對，數字對不上契約範本預設值又未見契約同步修改者，列為 `[退件]`：

| 比對項目 | 契約範本條號 | 預設值 |
| --- | --- | --- |
| 履約期限起算與日曆天／工作天 | 第七條（一）（二） | 未勾選者為日曆天 |
| 付款審核與撥付天數 | 第五條（一） | 各 15 工作天；補助款 30 工作天 |
| 驗收天數 | 第十二條（二） | 有初驗 7／30／20 日；無初驗 30 日 |
| 保固起算 | 第十三條（一） | 全部完成履約經驗收合格日起 |
| 逾期違約金比率與上限 | 第十四條（一）（五） | 每日 1‰（部分 3‰）；上限未載明者 20% |
| 智慧財產權 | 第十六條（三）5 | A～L 十二選項，須明確勾選 |

**智財只寫「著作財產權歸屬機關」而未對應 A～L 任一選項者，列為 `[建議]`**，並提醒範本註釋要求「避免因取得不必要之權利而增加採購成本」。

### 交付文件的名稱對不對得上契約

契約範本第二條（二）明列的文件為「工作計畫書、需求規格書、系統分析書、程式設計書、測試計畫書、執行報告書、教育訓練計畫書、軟硬體清冊及系統架構圖」。工作說明書使用 SRS／SDD 等業界慣稱而未標出對應項者，列為 `[建議]`——驗收時會出現「契約要系統分析書，廠商交 SDD」的爭執。

另查兩項契約範本已定、工作說明書漏寫廠商就不會做的事：**共通性應用程式介面規範**（第二條（四），國家發展委員會訂定）與**開放格式資料的產製頻率及銜接政府資料開放平臺**（第二條（二））。

### 評選項目表放對地方了嗎

投標須知範本（115.7.27 版）第五十八點載明最有利標之評選項目、標準及評定方式**如投標須知附件**。工作說明書與投標須知各有一份內容不同的評選項目表，列為 `[退件]`；只有一份而放在工作說明書並由投標須知指涉者，通過。

### 敏感資訊

工作說明書隨招標公告對外發布。文件中若出現機關實際 IP、內部網路架構圖、防火牆規則、資安設定值、帳號與密碼原則細節，列為 `[退件]`，建議改回 `【待填】`，於決標後以安全方式提供得標廠商。

# 用語與表達審查

審的是**逐字逐句**：用字對不對、承諾能不能驗收、句子指不指得出負責方。
機械性的部分交給 `scripts/check_wording.py`，語意的部分靠下方的規則人工判斷。

> 本檔同時是 `scripts/check_wording.py` 的**規則來源**。下方標記「【檢查規則】」的表格會被腳本讀取，
> 格式為 `| 避免用 | 建議改為 | 說明 |`，欄位順序與表頭文字請勿更動；要新增規則直接加一列即可。
> 同一列的「避免用」與「建議改為」若各以「、」分隔多個詞，須**一一對應、數量相同**。

## 語氣定位

公部門技術文件的語氣介於公文與技術報告之間：比公文白話，比技術部落格拘謹。原則是**平實、客觀、可查核**。

- 陳述事實用直述句，不用行銷語言。「本系統採三層式架構」而非「本系統採用業界領先的三層式架構」。  <!-- 檢查略過 -->
- 承諾用「應」「將」；描述現況用「係」「為」。避免「可能」「大概」「盡量」這類無法驗收的字眼。  <!-- 檢查略過 -->
- 第一人稱用「本公司」「本團隊」「本專案」，不用「我們」。  <!-- 檢查略過 -->
- 稱機關用全銜或「貴機關」（建議書中）／機關全銜（交付文件中）。交付文件屬技術文件，不必用公文的「鈞」「貴」等稱謂語，但建議書因帶有行文性質，可適度使用「貴機關」。  <!-- 檢查略過 -->

> 公文書（函、令、公告、開會通知單）的用語體例與此不同，不要互相套用。判斷準則：**這份文件會不會用機關發文字號發出去？** 會，就是公文書，交給公文 skill，本檔只審技術文件。

階層編號與圖表編號屬結構問題，見 `references/01-結構與格式.md`。

### 容易誤判、不列入自動規則的詞

以下由人工判斷，腳本不會攔：

| 詞 | 判斷方式 |
| --- | --- |
| 程序 | 指 program 時應改「程式」；指 procedure（作業程序、驗收程序、行政程序）是正確用法，不要改 |
| 登錄 | 指 log in 時應改「登入」；指「登錄有案」的登記行為是正確用法 |
| 品質保證 | 正確用語，不要看到「質保」兩字就改 |
| 客戶 | 政府對民眾提供服務時稱「民眾」或「使用者」；金融、電信等有商業契約關係的對象稱「客戶」是正確的，法遵語境的「確認客戶身分」亦然 |
| 質量 | 指 quality 時應改「品質」；指「質與量」（如「人才技能之質量」）是正確用法。兩者無法機械分辨，故不列入自動規則 |
| 內存 | 指 memory 時應改「記憶體」；但「範圍內存取」這類跨詞邊界的切法會誤判，故不列入自動規則 |
| 平台 | 「系統平台」宜改「資訊系統」，但「政府網站營運交流平台」等專有名稱照原名 |  <!-- 檢查略過 -->
| 界面／介面 | 本 skill 統一用「介面」。機關的交付項目說明附件若寫「界面設計規格」，以機關版本為準 |
| 國家通訊傳播委員會 | 腳本會標為[錯誤]，因為它常被誤寫成網站無障礙的主管機關（業務已移撥數位發展部）。若文中是因其他業務提到 NCC，屬正確用法，該行結尾加上略過標記即可 |  <!-- 檢查略過 -->

### 引用與專有名稱一律照原名

腳本比對的是字串，分不出這個詞是文章自己在用，還是在**引用別人的東西**。下列情形即使被標出來也不要改，該行行尾加上略過標記即可：

- 引用外國機構的報告或法規標題（例如世界經濟論壇的網路安全展望報告、紐約州金融服務業網路安全要求規範）。  <!-- 檢查略過 -->
- 引用我國既有文件的正式名稱（例如「政府網站 Web 2.0 營運作業參考指引（社會網絡篇）」）。  <!-- 檢查略過 -->
- 系統、平台、計畫的專有名稱（例如「人資串接平臺」「教育大數據分析」）。  <!-- 檢查略過 -->
- 契約條文的原文。

**改掉引用來源的用字，比留著不合慣例的用字更嚴重**——那會讓委員查不到原始出處。

## 數字用法

依行政院 93 年 9 月 17 日訂頒之「公文書橫式書寫數字使用原則」。**這一節與一般寫作習慣差最多，也最常被改。**

**用阿拉伯數字**（一般數字意義或統計意義）：

| 類別 | 例 |
| --- | --- |
| 代號、編號、發文字號 | 附表 1、院臺秘字第 0930086517 號 |
| **序數** | 第 1 階段、第 1 優先、第 2 次、第 3 名、第 4 季、第 5 會議室、第 6 次會議紀錄、第 7 組 |
| 日期、時間 | 民國 115 年 3 月 15 日、115 年度、7 時 50 分、延後 3 週辦理 |
| 電話、郵遞區號、門牌 | （02）1234-5678 |
| 計量單位 | 150 公分、2 萬元、7.36 公頃 |
| 統計數據 | 80%、6 億 3,944 萬 2,789 元、1：3 |  <!-- 檢查略過 -->
| 法規條項款目、引敘法規條文 | 依○○法第 44 條規定 |

**用中文數字**（描述性用語、專有名詞、慣用語）：

| 類別 | 例 |
| --- | --- |
| 描述性用語 | 一致性、三大面向、第一線、第二專長、三層式架構、一次性移轉 |
| 專有名詞 | 三國演義、五南書局 |
| 慣用語（星期、比例、概數） | 星期一、十分之一、三讀、約三、四天、七千餘人 |

> **最常錯的是序數。**「第一階段」「第二次會議」「第三季」依原則都應寫成「第 1 階段」「第 2 次會議」「第 3 季」。  <!-- 檢查略過 -->
> 但「第一線」「第二專長」屬描述性用語，維持中文數字。判斷方式：**數得出來的是序數（阿拉伯），形容性質的是描述（中文）。**

其餘：

- 年份用民國紀年為主，必要時併列西元：「115 年 3 月 15 日（2026 年）」。契約與履約期限依契約寫法。  <!-- 檢查略過 -->
- 金額用阿拉伯數字加千分位，並註明幣別與是否含稅。
- 中文與阿拉伯數字、英文之間留半形空格，可讀性較好（本 skill 各檔即採此寫法）。

## 標點符號與全形半形

依「立法慣用語詞及標點符號」與《文書處理手冊》的標點符號用法：

- **標題不使用標點符號。** 章節標題結尾不加句號、冒號。
- 中文行文一律使用**全形標點**：。，、；：？！「」『』（）——…
  - 並列的單字或詞語之間用**頓號「、」**，不是逗號：「功能需求、非功能需求、介面需求」。
  - 並列的短句或複句之間用**分號「；」**。
  - 有列舉的款、目之前用**冒號「：」**。
- **不要在中文句中混入半形標點**（`,` `;` `?` `!` 與半形括號）。這是 Word 自動轉換或從英文文件複製最常留下的痕跡。
- **英文、數字用半形，不要用全形**（不要寫 ＡＰＩ、２０２６）。程式碼、指令、檔名一律半形。  <!-- 檢查略過 -->
- 專有名詞的括號：中文內容用全形括號（），純英文或數字內容可用半形括號，但同一份文件要一致。
- **例外在分項標號**：機關要求比照公文分項標號時，標號的數字用全形而括號用半形（`１、`、`(1)`），與內文相反。規則見 `references/01-結構與格式.md` 第三節，本節只管內文。

> 腳本會用規則式檢查半形標點夾在中文之間、全形英數字、標題結尾帶標點、序數用中文數字四項，
> 這幾項是機械判斷，規則寫在 `scripts/check_wording.py`，不在本檔的表格中。

## 常見句型問題

- **主詞消失**：「將於系統測試階段完成介接測試」——誰做？技術文件的每個動作都要指得出負責方（本公司／機關／既有系統維護廠商）。
- **一句包三件事**：公部門審查逐句核對，一句一件事最不容易被誤解。
- **條件與結果分開寫**：「若機關未於期限前開放測試環境，本公司將…」比「本公司將視情況調整」清楚得多。  <!-- 檢查略過 -->
- **不要用問句與感嘆句**。
- **不要用「等等」「之類」結尾**：清單要窮舉，不能窮舉就寫「至少包含下列項目」。

## 用語造成的退件

結構面的退件原因見 `references/01-結構與格式.md`。純屬用語的有這幾類：

- 混用簡體字或中國大陸用語。
- 引用法規名稱不完整或已停止適用（見 `references/03-法規速查.md`）。
- 通篇形容詞、沒有可驗收的數字。
- 承諾用了「盡量」「必要時」「視情況」這類字眼，等於什麼都沒承諾。  <!-- 檢查略過 -->
- 動作找不到負責方，驗收時無法歸屬責任。

## 自動檢查

產出草稿後執行：

```bash
python scripts/check_wording.py 草稿.md
```

會依本檔的五張【檢查規則】表格（常見用字、用語偏好、不可驗收的字眼、行銷語言、法律統一用字）、
`references/03-法規速查.md` 的「已停止適用」清單、內建簡體字表，以及四項規則式檢查
（半形標點、全形英數字、標題結尾標點、序數用中文數字）逐行掃描，並列出全部 `【待填】`。

其他用法：

| 參數 | 用途 |
| --- | --- |
| `--rules` | 列出目前載入的全部規則與條數，可用來確認新增的規則有沒有被讀到 |
| `--只看錯誤` | 只列 [錯誤]；有 [錯誤] 時離開碼為 1，適合接 CI |
| `--無待填清單` | 不列 `【待填】` 清單 |

**從 PDF 或 Word 貼出來的草稿**，全形括號常在抽取過程被轉成半形，會湧出大量「改用全形括號」的 [建議]。那是抽取失真，不是原文的問題——先確認原始檔的寫法，不要照著改。

若某一行是**刻意**要提到禁用詞（例如檢核清單、用字對照說明），在**行尾**加上 `<!-- 檢查略過 -->` 即可跳過該行；統計會回報略過了幾行，不會靜默忽略。

**腳本抓的是機械性錯誤，語意仍須人工複核**；反過來說，腳本抓到的都是明確會扣分的項目，交件前應清乾淨。沒有檔案可跑時（例如在 ChatGPT 或 Gemini 上使用單檔版），就依上述五張表格與規則人工逐項比對。

## 一、資通安全

### （一）兩套分級不要混用

這是文件裡最常見的觀念錯誤：

- **資通安全責任等級（A、B、C、D、E 級）**：分級的對象是「**機關**」，依《資通安全責任等級分級辦法》核定，決定該機關應辦的資安事項（人力配置、稽核頻率等）。
- **資通系統防護需求分級（普、中、高級）**：分級的對象是「**個別資通系統**」，由機關就**機密性、完整性、可用性、法遵性**四個面向分別評估，**取其中最高者**作為該系統的防護需求等級，再依附表十「資通系統防護基準」實作對應控制措施。高級須實作中級與普級的措施（下含）。

文件中寫「本案系統屬中級」指的是後者。若要提機關的責任等級，須另外註明並確認機關已核定的等級，**不得自行推定**——不確定就寫 `【待填：機關資通安全責任等級】`。

### （二）「資通系統防護基準」的七大構面

附表十以七個構面、共 29 類控制措施編排：

1. 存取控制
2. 事件日誌與可歸責性
3. 營運持續計畫
4. 識別與鑑別
5. 系統與服務獲得
6. 系統與通訊保護
7. 系統與資訊完整性

文件中的「安全需求對照表」建議直接以這七個構面當左欄，逐項寫本案的實作方式，委員一眼就能對照。

### （三）附表十與「共通性資通安全基本要求」不是同一份

兩份都用高／中／普三級，但用途不同，寫文件時不要混為一談：

| | 《資通安全責任等級分級辦法》附表十「資通系統防護基準」 | 「各類資訊（服務）採購之共通性資通安全基本要求參考一覽表」 |
| --- | --- | --- |
| 管誰 | 機關自行或委外開發的資通系統，機關依法應實作的控制措施 | **採購時要寫進招標文件與契約的要求**，廠商應遵守 |
| 編排 | 七構面、29 類控制措施 | 依**資料或系統類型**分頁（雲端微服務 SaaS 套裝型、SaaS 辦公室生產力工具、資訊系統規劃服務等），每類再分資通安全項目 |
| 標示 | 依等級列出應辦事項 | ●－建議辦理；◎－經機關評估個案有必要辦理時 |
| 效力 | 依母法訂定 | 與「政府資訊服務採購作業指引」同函發布，**將納為資訊服務採購契約範本附件**；普級 113 年 3 月 1 日、中高級 113 年 8 月 1 日施行 |

一覽表的共通項目包括：資通安全管理措施或通過 CNS 27001／ISO 27001 等標準、涉個資時通過 CNS 27701／ISO 27701、不得為大陸地區廠商或第三地區含陸資成分廠商、日誌保存（帳號與權限變更、登入名稱、時間、IP 位址、資料存取及重要安全性事件，建議至少保存六個月）、供應商與產品安全佐證（公開漏洞回報應變機制、第三方檢測、OWASP TOP 10 檢測報告、行動應用 App 基本資安標章等）。雲端類另有資料不得移至本國以外地區、存取與備份備援的實體所在地不得位於大陸地區等要求。

**寫建議書或規格符合對照表時，先問機關本案適用哪一類、哪一級**，不要憑印象套。系統分級本身依附表十的分級原則判定，一覽表再依該級數選要求項目。

### （四）文件中應涵蓋

- **系統防護需求分級判定**：本案系統屬何級，四面向的評估結果與判定理由。
- **安全需求對照表**：依七構面逐項列出適用的控制措施與本案實作方式。
- **日誌紀錄規劃**：至少含使用者識別 ID（不得使用個資型態的識別）、經系統校時後的時間戳記、執行的功能或存取的資源、事件類型與結果。日誌的保存期限與防竄改機制一併說明。
- **第三方元件清單（SBOM）**：列出所使用的外部元件與軟體及其版本，並說明如何持續追蹤安全漏洞通告（CVE 資料庫、廠商安全通告）。
- **檢測規劃**：原始碼掃描、弱點掃描、滲透測試的時程、工具與缺失修補流程。行動應用另依「行動應用 App 基本資安檢測基準」辦理，並註明採用的版本號。

設計依據可援引 OWASP、SANS 等國際組織建議，但機關要看的仍是對照到附表十的實作說明。

## 二、無障礙

- **對外網站**：依「網站無障礙規範」辦理。等級分第 1 優先（A）、第 2 優先（AA）、第 3 優先（AAA），機關案多要求達 **AA 等級**並取得無障礙標章。檢測與標章業務由數位發展部辦理（無障礙網路空間服務網）。
  - 寫法上避免「符合無障礙規範 2.0 版 AA 等級」這種舊名稱，正確寫法是「符合『網站無障礙規範』AA 等級」。
- **無障礙政策的上位計畫**：行政院 113 年 8 月 9 日核定「普及與深化政府網站與行動化應用軟體無障礙設計行動方案（113-115 年）」。若本案期程落在該方案期間，機關可能引用其目標，撰寫前先問機關是否須對應。
- **機關內部公務系統**：另依「政府機關公務系統無障礙指引」，需考量視障、肢障同仁的操作需求，例如圖片按鈕須有替代文字、全功能須可鍵盤操作。內部系統通常不申請標章，但機關仍可能於驗收時要求自評。
- **行動應用**：依「行動版應用程式（APP）無障礙開發指引」；人工檢測項目檢核表係依「網站無障礙規範」的 4 原則、12 指引彙整而成。
- 文件中要寫的不只是「將符合 AA」，而是：檢測工具、檢測時點、發現問題的修正流程、標章申請時程。標章審核需作業時間，時程規劃要往前抓，不要壓在驗收前一週。

## 三、政府網站服務管理規範與數位服務指引

- **「政府網站服務管理規範」**：政府網站建置的遵循依據，適用入口網站、主題網站、分眾及外語網站。規範本文載明「本規範共 **11 條原則、32 項參考指引**」——**單位是「條原則」與「項參考指引」，不要寫成「11 項原則、32 條參考指引」**。規範採滾動修正，撰寫前請至政府網站營運交流平台確認現行版本。
- **「政府數位服務指引」**：引導以使用者為中心的服務設計，查證時為 13 項原則（發布機關為數位發展部數位政府司，該頁最後更新 114 年 3 月 4 日）。原則的數量與單位寫法請以指引總說明的原文為準——同性質的「政府網站服務管理規範」即寫作「條原則」而非「項原則」。配套自評工具的正式名稱為：
  - 「政府數位服務指引：政府資通訊應用計畫自評表」
  - 「政府數位服務指引：政府數位服務自評表」
- 另有「各機關資通訊應用管理要點」規範機關資通訊應用計畫的管理程序，若本案屬機關資通訊應用計畫項下，計畫書可能須配合該要點的查核機制。

若本案屬對民眾提供服務的網站或數位服務，文件中應說明如何對應上述規範，並在驗收前完成自評表。

## 五、智慧財產權與原始碼

**先確認契約寫的是「歸屬」還是「授權」，不要預設。** 過去多數契約要求著作財產權歸屬機關，但「政府資訊服務採購作業指引」（112 年 9 月 25 日）第五點之（六）已改變政策方向：

> 機關與廠商約定履約標的著作權歸屬時，應考量機關與廠商間之平衡，先評估原始碼無洩漏或被竊取不當使用之風險，並依風險採取必要措施。另為利後續系統維護管理及功能增修，機關應儘量以取得**著作財產權之授權利用**為優先，包括轉授權或再製權等。  <!-- 檢查略過 -->

因此文件裡不要一律寫「著作財產權歸屬機關」——**以該案契約條文為準**，契約未明訂時寫 `【待填：著作權歸屬或授權方式】`，不要替機關決定。

**契約條文長什麼樣：不是二選一，是十二選一。** 資訊服務採購契約範本（113 年 12 月 26 日修正）第十六條（三）5 列 A 至 L 共 12 種約定方式供機關勾選，涵蓋「廠商為著作人、機關取得指定之著作財產權授權」（A，另須就重製、公開口述、公開播送、公開上映、公開演出、公開傳輸、公開展示、改作、編輯、出租 10 項逐項勾選）、「著作財產權於完成同時讓與機關」（B）、「機關與廠商共有」（D）、「以機關為著作人並取得著作財產權全部」（H）等。範本註釋另載明：

> 機關亦宜考量避免因取得不必要之權利而增加採購成本。  <!-- 檢查略過 -->

並建議非完全客製化之著作（例如與其他機關使用共同模組者，如公文系統模組）約定由廠商享有著作人格權及著作財產權，機關享有非專屬、永久、無償利用並得再轉讓授權第三人之權利；涉及安全性質（例如電子申請）、客製化或其他特殊目的者，則建議由機關享有著作財產權。

審查時：文件只寫「著作財產權歸屬機關」而未對應上列任一選項者列為 `[建議]`，並指出應載明對應契約第十六條（三）5 的哪一項與哪幾項權利。

**機關資料的所有權不必爭取，契約已經給了。** 同條（三）4 明定廠商所取得或持有機關之資料（文字、影像、圖形、聲音，不論儲存於何種媒體）皆屬機關所有，且除為提供服務所需、法令規定或經機關書面同意外，不得複製、揭露或交付第三人。文件寫出比這更弱的版本，列為 `[退件]`。

不論歸屬或授權，文件中都應載明：交付的原始碼範圍、建置環境與相依套件清單、編譯與部署程序、所使用的開源元件及其授權條款。**契約範本第十六條（三）6 另要求使用開源軟體者，應依其授權範圍授權機關利用，並以執行檔及原始碼共同提供之方式交付，並交付開源軟體清單。**

具傳染性的開源授權（如 GPL 系列）與著作財產權歸屬機關可能產生衝突，元件選用階段就要確認，不要等到驗收才發現。

## 六、生成式 AI 使用限制

依《行政院及所屬機關（構）使用生成式 AI 參考指引》（行政院 112 年 8 月 31 日核定），**機關（構）製作機密文書不得使用生成式 AI**，且人員不得向生成式 AI 提供涉及機密業務或個人資料之訊息；使用生成式 AI 協助執行業務時，業務承辦人仍須負最終審核與判斷責任。撰寫本類文件時：

- 不輸入機關未同意公開的網路架構、實際 IP、帳號與密碼原則細節、資安設定值。
- 系統管理手冊、資安相關章節的敏感欄位一律留 `【待填】`。
- 不輸入與案件無關的個資。
- 該指引採滾動修正，引用前確認現行內容。

# 官方來源與查證狀態

本檔是本組 skill 所引用官方文件的**出處清單**，供 `scripts/check_sources.py` 定期比對頁面是否已改版。

**為什麼需要這一份。** 這些文件更新頻率不一，且不會通知引用者。實例：投標須知範本於 115 年 7 月 27 日改版，本專案原本記載的 112 年 6 月 30 日版落後三年；數位發展部的「資訊服務採購契約範本（含投標須知範本）之資安檢核事項」至查證時仍依據舊版投標須知範本。**官方文件引用官方文件的舊版是常態，不是例外。**

政府文件送出後不易更正，引用過時版本在審查與履約爭議時要負責。因此本專案的規則是：**寧可只寫法規全名而不寫版本，也不要寫錯版本**；必須寫版本時，以本表為準並自行複查。

## 怎麼用

```bash
python scripts/check_sources.py              # 逐項連線比對
python scripts/check_sources.py --list       # 只列清單，不連線
python scripts/check_sources.py --只看異動   # 只列需要人工確認的項目
python scripts/check_sources.py --嚴格       # 連不上也視為未通過（送件前用）
```

**`[無法連線]` 不等於沒有異動**——那幾項這次根本沒查到。逾時會自動重試一次，仍失敗時預設離開碼還是 0（政府網站偶有維護，不該讓排程紅燈），但送件前查證請加 `--嚴格`，有來源連不上就回離開碼 2。

比對方式看「識別字串」欄的形態，分兩種：

| 識別字串形態 | 比對方式 | 判為 `[異動]` 的條件 |
| --- | --- | --- |
| 民國七位日期（如 `1150727`） | 掃出頁面上所有合法民國日期取最大值**比大小** | 出現比記載更新的日期 |
| 其他（發文字號、文件名稱） | 找字串 | 字串消失 |

日期要比大小而不是找字串，是因為工程會範本頁面**新版在前、歷史版本並列**：舊版號永遠留在頁面上，單純搜尋字串會一直回報相符，偵測不到改版——本專案落後三年的投標須知範本正是這樣漏掉的。

腳本不判斷新版本改了什麼，只負責提醒你去看。有 `[異動]` 時離開碼為 1，可用於排程。

無網路時用 `--list` 取得網址自行查閱。
