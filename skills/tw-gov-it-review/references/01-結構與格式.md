# 結構與格式審查

審的是**看得見的骨架**：章節有沒有缺、編號對不對、圖表有沒有掛上、追溯鏈接不接得起來。
這一類問題不需要讀懂內容就能判斷，也是驗收時最先被抓的。**缺章節比內容普通嚴重得多。**

## 一、章節完整性

判斷順序有先後，不要顛倒：

1. **機關的「交付項目文件說明」附件**——有這份就以它為準，逐項打勾，機關要的章節名稱一字不改。
2. 沒有機關版本時，才用 `../tw-gov-it-docs/references/02-交付文件規格.md` 的通用章節規格對照。

通用規格是底稿，不是規範。文件多了機關沒要求的章節不算缺失；**少了機關要求的章節就是退件**。

**通用規格以網站型系統為預設，未覆蓋行動應用（App）與 AI 專案。** 審這兩類文件時，只審通用章節與追溯鏈，不要拿通用規格判定 App 或 AI 專屬章節缺漏——缺什麼沒有依據，判了就是誤報。改為向使用者說明這一段需依機關要求自行確認。

各文件的必備段落（不分機關版本，缺了都會被問）：

| 段落 | 說明 |
| --- | --- |
| 封面 | 案名、機關全銜、廠商全銜、文件名稱、版本、日期 |
| 文件版本紀錄表 | 版本、日期、修訂人、修訂內容摘要。版本編號不得跳號 |
| 目錄 | 含圖目錄、表目錄；頁碼須與內文一致 |
| 名詞對照表 | 全案共用一份，避免同一功能在不同文件叫不同名字 |

## 二、追溯鏈

這是本組文件的骨幹，也是審查的重點。五段任一段斷掉，整條鏈就失效：

```
RFP 需求編號 → 軟體需求 → 設計元件 → 驗證方式 → 單元測試案例 → 整合測試案例
```

審查方式：

- 取需求追溯表，確認**每一條 RFP 需求都出現在左欄**，沒有需求被漏掉。
- 反向抽驗：任取一個測試案例編號，往回追到需求編號，中間不能斷。
- 代號體系是否全案一致（需求、元件、介面、報表、程式、資料表各有前綴，且不混用）。
- 需求增刪後追溯表有沒有跟著更新——這是最常見的斷點。

追溯表對不起來時，指出**斷在哪一段**，不要只說「追溯性不足」。

## 三、階層編號

公部門標準階層：

```
壹、貳、參、肆…        （章）
一、二、三…            （節）
（一）（二）（三）…     （項）
1. 2. 3.               （目）
(1) (2) (3)            （細目）
```

- 正文用中文階層，技術附錄可用 1.1.1 這類阿拉伯數字多層編號。
- 階層不得跳階（壹之下直接出現「（一）」）。
- 同一層級的編號樣式全文一致。

## 四、圖表

- 每張圖表都要有編號、標題，並在正文中被引用（「詳如圖 3-1」）。**孤立的圖表一定會被問。**
- 圖表編號用「圖 3-1」「表 3-1」（章-序），全文一致。
- 系統架構圖至少三張：整體架構圖、網路架構圖、資料流圖。
- 甘特圖要標出查核點與交付物，橫軸與履約期限對齊。
- 螢幕截圖清晰，敏感資料須遮蔽。

## 五、合規章節有沒有到位

這一節審的是「**該有的合規段落在不在**」，內容正不正確見 `references/03-法規速查.md`。

| 章節 | 缺了會怎樣 |
| --- | --- |
| 系統防護需求分級判定（普／中／高）與四面向評估理由 | 資安章節的地基，缺了後面整段沒有依據 |
| 安全需求對照表（依「資通系統防護基準」七構面編排） | 委員無法逐項對照 |
| 日誌紀錄規劃（四要素） | 驗收必查 |
| 第三方元件清單 | 漏洞追蹤無從談起 |
| 檢測規劃（原始碼掃描、弱點掃描、滲透測試） | 時程表若沒納入，驗收前才做來不及 |
| 無障礙等級、檢測時點與標章申請時程 | 標章審核需作業時間，壓在驗收前一週就是風險 |
| 個資處理（項目、目的、保存期限、去識別化） | |
| 原始碼交付範圍與智財歸屬、開源授權相容性 | |

## 六、一致性

跨文件的對照，單看一份文件看不出來，要並排比：

- 功能名稱一致（SRS 叫「案件管理」，SDD 不能叫「案件維護」）。
- 代號體系一致。
- 清單筆數與明細筆數相符。
- 機關名稱、案名全文正確，**無沿用他案殘留**——這是最傷信任的錯誤，交件前全文搜尋確認。
- 目錄頁碼與內文一致（改完內容忘記更新目錄是最常見的退件原因）。

## 七、敏感欄位該留白的有沒有留白

依《行政院及所屬機關（構）使用生成式 AI 參考指引》，**機密文書應由承辦人親自撰寫**。審查時要反過來確認「不該寫的有沒有被寫進去」：

- 真實 IP、實際網路架構、帳號與密碼原則細節、資安設定值、開放埠清單。
- 截圖是否已遮蔽敏感資料。
- 系統管理手冊與營運交接文件敏感度最高：這兩份的敏感欄位只應記錄「用途與保管方式」，實際值由雙方另行以安全方式交付。

發現這類內容寫進去了，列為**退件等級**，並建議改回 `【待填：○○】` 由承辦人自行補上。

## 八、審的是機關自己寫的 RFP 時

機關承辦人也會拿需求說明書或建議書徵求文件來審。政府資訊委外服務團依實際受理的機關諮詢案件，歸納出 7 項常見問題（《政府機關資訊通報》第 325 期，103 年 11 月），可以直接當檢查項目：

| 常見問題 | 審查時看什麼 |
| --- | --- |
| 需求規格不明確或不合理 | 文字是否籠統到機關與廠商日後會解讀不一；是否僅就現有廠商所提建議改寫（有綁標之虞） |
| 專案管理規範不足 | 有無要求廠商的專案管理計畫涵蓋專案組織、工作流程與查核點、定期工作報告與會議、風險與變更管理、品質管理、測試驗收計畫 |
| 服務水準（SLA）要求不合理 | 過嚴會導致廠商必然違約，過寬則上線後效能不彰；項目選用見 `../tw-gov-it-docs/references/04-履約與維運文件.md` 第五節 |
| 文件品質不佳或架構缺乏整體性 | 結構是否鬆散、重要需求項目遺漏或重複描述、前後矛盾 |
| 現行資訊作業環境未適當描述 | 投標廠商不清楚機關環境，描述過簡會讓廠商無法正確評估投入資源 |
| RFP 內容與契約書條文無法適當匹配 | 招標須知與契約書多由總務單位統一制訂，RFP 由資訊承辦人研擬，兩者容易矛盾 |  <!-- 檢查略過 -->
| 需求項目超出預算金額 | 需求規格明顯超出預算會使優良廠商不願投標 |

該文另提供「RFP 內容大綱撰寫建議」，分七章：專案概述、現況及問題說明、專案工作需求、專案管理需求、驗收與付款、建議書製作規定、評選作業，並依專案規模標示各節為必要或視需要。**該文為 103 年資料，其自訂的專案規模金額分級不是現行法定門檻**，章節結構可參考，金額級距請改依現行採購規定與「政府資訊服務採購經費估算編列手冊」。

## 結構與格式檢核清單

- [ ] 章節與機關「交付項目文件說明」逐項對照，無缺漏（無機關版本時對照通用規格）
- [ ] 封面、文件版本紀錄表、目錄（含圖目錄、表目錄）齊備
- [ ] 目錄頁碼與內文一致
- [ ] 版本紀錄表已更新，版本編號未跳號
- [ ] 追溯鏈五段皆可對應，需求追溯表無遺漏需求
- [ ] 測試案例編號可回連需求編號
- [ ] 代號體系全案一致
- [ ] 階層編號符合公部門慣例，未跳階
- [ ] 圖表皆有編號、標題，且於正文被引用
- [ ] 系統架構圖、網路架構圖、資料流圖齊備
- [ ] 合規章節（防護分級、安全需求對照表、日誌、元件清單、檢測、無障礙、個資、智財）皆在
- [ ] 全案功能名稱一致，機關名稱與案名無他案殘留
- [ ] 清單筆數與明細筆數相符
- [ ] 未寫入真實 IP、帳號、密碼原則細節；截圖已遮蔽
- [ ] 所有 `【待填】` 已標示清楚，並列成清單交給使用者補實
