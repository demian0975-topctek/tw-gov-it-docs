# 顧問協辦工作說明書撰寫

顧問手上沒有機關內部才知道的事實，卻要交出一份精確到能送審的文件——這是這個 skill 唯一要解決的問題。
撰寫要點、訪談技巧、交付慣例見 `references/01-顧問協辦工作說明書撰寫要點.md`；骨架見
`assets/工作說明書骨架.md`。

## 三步驟

1. **訪談蒐集機關專屬事實。** 依 `references/01` 第二節的訪談技巧，問出金額、期程這類機關以外沒人
   答得出來的事實；答不出來的當場記下「這個數字我該問誰」，不要用常見規格代填。
   完成準則：`references/01` 第一節列出的六類事實，每一類都已問到答案，或明確記下待確認對象。

2. **套用骨架產出草稿。**

   ```bash
   python scripts/make_docx.py
   ```

   骨架章節與措辭取自實際結案案例（見 `assets/工作說明書骨架.md` 開頭說明），不是通用理論架構。
   已訪談到答案的欄位直接改掉骨架裡對應的 `○○○`；答不到的維持 `○○○`，不要用合理猜測填上去——
   這是**不編造**在這個 skill 裡的落地方式，與是否為「機關專屬」無關，凡是換一個採購案就會不一樣
   的數字或名稱都算。輸出檔名固定為 `工作說明書_V0.0.docx`。
   完成準則：草稿裡每一個 `○○○` 都能對應到「已填實」或「待確認清單裡的一條」，沒有第三種狀態。

3. **交付草稿。** 待確認事項清單（列出所有 `○○○` 對應到哪一條、要問誰）在對話或另附文件裡交代，
   **不要寫進 Word 檔本身**——草稿要維持乾淨、可直接印出的樣子。交付前跑一次 `references/01` 第五節
   的自我檢查表。
   完成準則：自我檢查表每一項都有結論，機關拿到的是「一份乾淨的草稿＋一張待確認清單」，不是夾雜
   顧問備註的半成品。

## 這幾項不要自己動手改

- **不編造。** 技術數據、法規條號、人名、機關內部環境資訊，未知一律留 `○○○`，不得代為編造。
  政府文件送出後不易更正，引錯要負責。
- **不寫敏感資訊。** 真實 IP、網路架構、帳號密碼原則、資安設定值、開放埠清單都不寫進草稿。依
  《行政院及所屬機關（構）使用生成式 AI 參考指引》，機密文書應由承辦人親自撰寫。
- **機關版本優先。** 機關已有自訂章節或格式時，以機關版本為準，不要拿骨架去否定機關的要求。

## 範圍界線

只處理「機關委託顧問協辦撰寫工作說明書」這一種情境與這一種文件。要從頭寫其他種類的交付文件
（建議書、SRS、SDD、手冊、計畫書）、或情境是機關／廠商自行撰寫而非委託顧問代筆，改用
`tw-gov-it-docs`；審查已經寫好的文件，改用 `tw-gov-it-review`。
